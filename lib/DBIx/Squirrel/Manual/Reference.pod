=head1 NAME

DBIx::Squirrel::Manual::Reference - DBIx::Squirrel reference

=head1 DESCRIPTION

DBI, minus the boilerplate, plus a pipeline.

With DBIx::Squirrel, you still write SQL, as you do with the DBI. It
takes away the friction around it: placeholders in whatever style you
like, lists of values, iterators over results, rows as objects, and a
pipeline of stages written beside the query. It's a subclass of the
DBI, so everything the DBI does still works. Where the two do the same
thing, they give the same result.

This reference describes every method, attribute, function and
message, and the protocols other code can rely on. Its chapters follow
the L<user guide|DBIx::Squirrel::Manual::HowTo>'s, a layer at a time from the DBI up, and
each links to its chapter there: the guide is the tour, this is the
map. Each module's own POD says the same things more briefly. Where
the two differ, the POD is the authority. Every example runs, against
the database below, and its comments say what it prints.

This is version 3. L<Upgrading from 2.x|/"Upgrading from 2.x"> and
L<Upgrading from 1.x|/"Upgrading from 1.x"> list what changes for code
written for earlier versions.

=head1 The examples' database

The examples run against this SQLite database, the user guide's, a
file called C<music.db>. They follow on from each other, so C<$dbh> is
this handle wherever it appears. It imports everything from
L<DBIx::Squirrel::Tooling|/"Importing: DBIx::Squirrel::Tooling">, so the
examples needn't.

    use v5.36;
    use DBIx::Squirrel;
    use DBIx::Squirrel::Tooling qw(:all);    # every stage, sink and word

    my $dbh = DBIx::Squirrel->connect('dbi:SQLite:dbname=music.db', {RaiseError => 1, PrintError => 0});

    $dbh->do("DROP TABLE IF EXISTS $_") for qw(track album artist);
    $dbh->do('CREATE TABLE artist (id INTEGER PRIMARY KEY, name TEXT)');
    $dbh->do('CREATE TABLE album  (id INTEGER PRIMARY KEY, artist_id INTEGER, title TEXT, year INTEGER)');
    $dbh->do('CREATE TABLE track  (id INTEGER PRIMARY KEY, album_id INTEGER, name TEXT, plays INTEGER)');

    $dbh->do('INSERT INTO artist (name) VALUES (?)', $_) for 'Abba', 'Blur', 'Cream';
    $dbh->do('INSERT INTO album (artist_id, title, year) VALUES (?, ?, ?)', @$_)
        for [1, 'Arrival', 1976], [2, 'Parklife', 1994], [2, 'The Great Escape', 1995],
            [3, 'Disraeli Gears', 1967];
    $dbh->do('INSERT INTO track (album_id, name, plays) VALUES (?, ?, ?)', @$_)
        for [1, 'Dancing Queen', 9100], [1, 'Knowing Me, Knowing You', 4200],
            [2, 'Girls & Boys', 6100], [2, 'Parklife', 5800],
            [3, 'Country House', 3900], [4, 'Sunshine of Your Love', 7700];

=head1 At a glance

    use DBIx::Squirrel::Tooling qw(:all);    # every stage, sink and word

    # Placeholders in the style you like: ?, ?1, :1, $1, :name or $name
    my $sth = $dbh->prepare('SELECT name FROM artist WHERE id = :id');
    $sth->execute(id => 2);
    say $sth->fetchrow_arrayref->[0];    # Blur

    # A placeholder with ... takes a list: a ? for each of its values
    my $names = $dbh->selectcol_arrayref('SELECT name FROM artist WHERE id IN (...:ids) ORDER BY id', ids => [1, 3]);
    say "@$names";    # Abba Cream

    # An iterator over the rows, read as they're wanted
    my $it = $dbh->iterate('SELECT name FROM artist ORDER BY id');
    while (my($row) = $it->next) {
        say $row->[0];
    }
    # Abba
    # Blur
    # Cream

    # Stages beside the query, and a sink last to say what comes back
    my @top = $dbh->iterate(
        'SELECT name FROM track ORDER BY plays DESC',
        pluck('name'),
        take(2),
        keep_all,
    );
    say join ', ', @top;    # Dancing Queen, Sunshine of Your Love

    say $dbh->iterate('SELECT * FROM track WHERE plays > ?', 6000, count_items);    # 3

    # Each row as an object, with a method for each column
    say $dbh->results('SELECT * FROM album WHERE id = ?', 2)->first->title;    # Parklife

=head1 Importing: DBIx::Squirrel::Tooling

    use DBIx::Squirrel::Tooling qw(:all);               # everything below
    use DBIx::Squirrel::Tooling qw(:stages :sinks);     # or some tags
    use DBIx::Squirrel::Tooling qw(pluck keep_all);     # or some names

described below. DBIx::Squirrel::Tooling exports all of it, from one

B<Made in:> L<Stages::Flow|/"Taking and dropping">

=item C<:batch>

B<Holds:> C<batch>, C<collect>

B<Made in:> L<Stages::Batch|/"Batching and collecting">

=item C<:taps>

B<Holds:> C<peek>, C<count_into>, C<dump_to>

B<Made in:> L<Stages::Taps|/"Canned stages">

=item C<:rows>

B<Holds:> C<pluck>, C<as_hash>

B<Made in:> L<Stages::Rows|/"Canned stages">

=item C<:stages>

B<Holds:> C<:flow>, C<:batch>, C<:taps> and C<:rows>

=item C<:context>

B<Holds:> C<iterator>, C<result_number>, C<result_original>

B<Made in:> L<Context|/"Context">

=item C<:sources>

B<Holds:> C<from_array>, C<from_fh>, C<from_file>, C<counter>

=item C<:sinks>

=item C<:json>

B<Holds:> C<from_json>, C<from_jsonl>, C<to_json>, C<to_jsonl>

B<Made in:> Ekorn::Pipeline::Factories

=item C<:all>

B<Holds:> all of the above

=back

=over 4

=item *

B<Nothing by default.> Ask for tags, names, or both. An unknown tag
or name is Exporter's error: it warns C<"%s" is not defined in
%DBIx::Squirrel::Tooling::EXPORT_TAGS>, or C<"%s" is not exported by
the DBIx::Squirrel::Tooling module>, and dies C<Can't continue after
import errors>.

=item *

B<The same subs.> Each name is the sub its own module exports,
prototype and all, so C<take_if { ... }> and C<stage { ... }> parse as
they do imported from there, and importing a name from both does no
harm.

=item *

B<DBIx::Squirrel's, where both export a name.> Each name comes from
DBIx::Squirrel's own module where it has one, and from
Ekorn::Pipeline's only where it has none. Today each name both
export is the same sub, so importing Ekorn::Pipeline::Tooling too,
in either order, gives the same subs. A test fails if that changes.

=item *

B<What's left out.> What's for extending DBIx::Squirrel rather than
using it, such as C<croakf>, from DBIx::Squirrel::Errors, and
C<is_stage>, from Ekorn::Pipeline; L<the
Sugar|/"12. Sugar: a function for each database and statement">, whose
C<use> makes functions; and L<C<E<verbar>>|/"11. Operators: E<verbar> and @{}">, which only
C<use Ekorn::Pipeline::Operators> puts in force, in its own scope.

=item *

B<JSON.pm's names.> JSON exports a C<from_json> and a C<to_json> of
its own, by default, so a module using both imports C<:all> or C<:json>
from only one of them, or calls the other's by its full name.

=item *

B<What a tag holds is public.> A name may be added to one in a
release that only adds, but is dropped or renamed only in a major
release.

=back

=head1 1. Connecting

The user guide's L<chapter 1|DBIx::Squirrel::Manual::HowTo/"1. Still the DBI">.

=head2 Importing

C<use DBIx::Squirrel> takes the names the DBI exports, as C<use DBI>
does, and the DBI exports them:

    use DBIx::Squirrel qw(:sql_types neat);

    say SQL_INTEGER;    # 4
    say neat('Abba');   # 'Abba'

=head2 connect

    $dbh = DBIx::Squirrel->connect($data_source, $username, $password);
    $dbh = DBIx::Squirrel->connect($data_source, $username, $password, \%attr);
    $dbh = DBIx::Squirrel->connect($data_source, \%attr);
    $dbh = DBIx::Squirrel->connect($dbh, \%attr);

C<connect> connects to a data source, as the DBI's C<connect> does, and
returns a database handle, a C<DBIx::Squirrel::db>. Its statement
handles are C<DBIx::Squirrel::st>s. Both are subclasses of the DBI's
own, so they do everything the DBI's handles do.

The username and password can be left out, with the attributes
straight after the data source.

Unlike the DBI's C<connect>, it B<always croaks> if the connection
fails, whatever C<RaiseError> is set to. The message is the one the DBI
raises under C<RaiseError>, such as
C<DBIx::Squirrel connect('dbname=music.db','',...) failed: ...>, and
it's reported at the line that called C<connect>. The DBI returns
C<undef> without C<RaiseError>.

    eval { DBIx::Squirrel->connect('dbi:NoSuchDriver:x', {RaiseError => 0, PrintError => 0}) };
    say $@ ? 'croaked' : 'returned';    # croaked

=head2 Connecting with an existing handle

Given a database handle in place of a data source, C<connect> makes a
new connection with the same parameters, using the DBI's C<clone>. Any
attributes passed are applied to the new connection. The handle can
come from DBIx::Squirrel, from the DBI itself, or from code that made
its own connection. So a plain DBI handle can be turned into
DBIx::Squirrel's:

    use DBI;

    my $plain    = DBI->connect('dbi:SQLite:dbname=music.db', '', '', {RaiseError => 1});
    my $squirrel = DBIx::Squirrel->connect($plain);
    say ref $squirrel;    # DBIx::Squirrel::db

The new handle keeps the first one's C<ekorn_> defaults. Any passed
take their place. It's a separate connection, not a second name for
the first. It doesn't share the first one's transaction, temporary
tables or session settings. An in-memory SQLite database, for example,
gives a new, empty database.

=head2 DBIx::Squirrel's own attributes

Attributes whose names start C<ekorn_> are DBIx::Squirrel's own. They
aren't passed on to the DBI. Passed to C<connect>, they're the defaults
for every statement the handle prepares. Passed to C<prepare> (or
C<prepare_cached>, C<do>, C<iterate>, C<results> and the select methods),
they override those defaults for one statement.

=over 4

=item C<ekorn_dialect>

The database whose rules statements are read by, such as C<mysql> or C<Pg>. C<connect> works it out when it isn't given. See L<The dialect|/"The dialect">.

=item C<ekorn_finish_active>

When true, a statement still active from an earlier C<execute> is finished before it's executed again. See L<execute|/"execute">.

=item C<ekorn_slice>

The shape an iterator fetches rows in: an array reference for arrays, the default, or a hash reference for hashes. See L<Rows as arrays or hashes|/"Rows as arrays or hashes">.

=item C<ekorn_result_class>

The base class of a result set's row objects, a subclass of C<DBIx::Squirrel::Result>. See L<Methods of your own|/"Methods of your own">.

=back

    my $hashes = DBIx::Squirrel->connect('dbi:SQLite:dbname=music.db', {
        RaiseError  => 1,
        ekorn_slice => {},    # iterators fetch hashes, by default
    });
    say $hashes->iterate('SELECT name FROM artist WHERE id = 1')->first->{name};                        # Abba
    say $hashes->iterate('SELECT name FROM artist WHERE id = 1', {ekorn_slice => []})->first->[0];    # Abba

=head2 The dialect

Statements are read by the rules of the database they're for: where
strings start and end, and what's a comment (see
L<Placeholders|/"2. Placeholders">). The dialect is given in the
C<ekorn_dialect> attribute. When it isn't, C<connect> works it out:

=over 4

=item *

It's the driver's own name, such as C<SQLite>, C<mysql> or C<Pg>.

=item *

A driver that passes the connection on to another database
(DBD::ADO, DBD::Gofer, DBD::JDBC, DBD::ODBC or DBD::Proxy) is asked,
through the DBI's C<get_info>, what the database is. MariaDB, MySQL,
PostgreSQL and SQLite are recognised.

=item *

Any other database, or one that doesn't say, is read by the standard
rules.

=back

Name the dialect when C<connect> can't tell:

    $dbh = DBIx::Squirrel->connect($odbc_data_source, $username, $password, {ekorn_dialect => 'mysql'});

=head2 Subclassing

Called on a subclass of DBIx::Squirrel, C<connect> uses that subclass's
database and statement handle classes. The DBI requires the subclass
to have both, and each must be a subclass of DBIx::Squirrel's:

    package My::Squirrel     { our @ISA = 'DBIx::Squirrel' }
    package My::Squirrel::db { our @ISA = 'DBIx::Squirrel::db' }
    package My::Squirrel::st { our @ISA = 'DBIx::Squirrel::st' }

    my $mine = My::Squirrel->connect('dbi:SQLite:dbname=music.db', {RaiseError => 1});
    say ref $mine;    # My::Squirrel::db

Without them, the DBI warns that the subclass isn't set up, and
returns its own handles.

=head1 2. Placeholders

The user guide's L<chapter 2|DBIx::Squirrel::Manual::HowTo/"2. Writing statements">.

=head2 The styles

A statement can use placeholders in any of these styles. Each is
rewritten as C<?> before the DBI sees it:

=over 4

=item C<?>

B<Example:> C<WHERE id = ?>

B<How values are bound:> In order, as with the DBI.

=item C<?1>

B<Example:> C<WHERE id = ?1>

B<How values are bound:> By number, from 1.

=item C<:1>

B<Example:> C<WHERE id = :1>

B<How values are bound:> By number, from 1.

=item C<$1>

B<Example:> C<WHERE id = $1>

B<How values are bound:> By number, from 1.

=item C<:name>

B<Example:> C<WHERE id = :id>

B<How values are bound:> By name.

=item C<$name>

B<Example:> C<WHERE id = $id>

B<How values are bound:> By name.

=back

A statement uses B<one style> throughout. C<prepare> croaks if it
finds more than one, listing each as an example:
C<Expected one placeholder style, not several (?, :name)>.

The same placeholder can appear more than once:

=over 4

=item *

A B<numbered> placeholder is bound once, wherever it appears. In
C<SELECT $2 + $1, $1>, the values C<(10, 20)> give
C<SELECT 20 + 10, 10>. There must be as many values as the highest
number, and numbers start from 1.

=item *

A B<named> placeholder is bound by name, wherever it appears.
Values are given as pairs or in a hash reference, with or without
the sigil. There must be a value for each name, and no other.

=back

    say join ' ', $dbh->selectrow_array('SELECT $2 + $1, $1', 10, 20);    # 30 10

    my $sth = $dbh->prepare('SELECT name FROM artist WHERE id = :id OR id = :id + 10');
    $sth->execute(id => 2);
    say $sth->fetchrow_arrayref->[0];    # Blur
    $sth->execute({':id' => 3});
    say $sth->fetchrow_arrayref->[0];    # Cream

=head2 Lists

A placeholder with C<...> before it takes a list. It's written as a C<?>
for each of its values, separated by commas. Use it for C<IN>, and
anywhere else SQL takes a list of values:

    my $names = $dbh->selectcol_arrayref('SELECT name FROM artist WHERE id IN (...:ids) ORDER BY id', ids => [1, 2]);
    say "@$names";    # Abba Blur

Any style can take a list: C<...?>, C<...?1>, C<...:1>, C<...$1>,
C<...:name> or C<...$name>. The list is a reference to an array of at
least one plain value. It's given as any other value is: by name, or
in order. Given to a statement whose one value is a list, a single
array reference is the list, not the values in it:

    my $one = $dbh->selectcol_arrayref('SELECT name FROM artist WHERE id IN (...?) ORDER BY id', [1, 3]);
    say "@$one";    # Abba Cream

    my $two = $dbh->selectcol_arrayref('SELECT name FROM artist WHERE name = ? OR id IN (...?) ORDER BY id', 'Abba', [2]);
    say "@$two";    # Abba Blur

=over 4

=item *

B<It's prepared with its values.> How many values a list has
decides the statement the DBI prepares. So a statement taking a list
is prepared by a method given its values: C<do>, the select methods,
C<iterate>, C<results>, and the Sugar's functions. C<prepare> and
C<prepare_cached> croak:
C<Expected bind values with a statement taking a list (...:ids)>.

=item *

B<A list has at least one plain value.> An empty list croaks, as
C<IN ()> isn't SQL, so the empty case is left to you:
C<Expected at least one value in a list (...:ids)>. So does a plain
value or C<undef> in place of a list. So does a list holding a
reference, such as C<[[1, 2, 3]]> to a statement whose one value is a
list.

=item *

B<A placeholder takes a list everywhere it's used, or nowhere.>
Used twice, it takes its list in both places.

=item *

B<Its handle is for lists of the lengths it was prepared for.> The
statement handle of a statement taking a list, such as an iterator's
C<sth>, can be executed again with lists of the same lengths. Given
another length, it croaks. An iterator's L<C<reset>|/"reset"> prepares
the statement again, on a new handle, when a list has a different
number of values. A Sugar statement taking a list isn't cached, as
each length makes a different statement.

=item *

B<Databases limit the values in a statement.> A very long list can
fail to prepare, as the same statement would with plain DBI.

=back

With DBD::Pg, C<= ANY(?)> given an array reference, as a PostgreSQL
array, is one statement whatever the array's length. The two don't mix
up. A list placeholder's array is its list, and any other
placeholder's is a PostgreSQL array. C<pg_placeholder_dollaronly>
leaves the statement to DBD::Pg, so under it no placeholder can take a
list.

=head2 What isn't a placeholder

Placeholders are looked for only in the SQL itself. These are left
unchanged:

=over 4

=item *

anything inside a quoted string or identifier: C<'10:30'>, C<"a:b">,
C<> C<c?> C<>;

=item *

comments: C<-- :x>, C</* $1 */>;

=item *

PostgreSQL's dollar-quoted bodies: C<$$ ... $$>, C<$tag$ ... $tag$>;

=item *

a cast, such as C<x::int>;

=item *

an identifier containing C<$>, such as C<v$session>.

=back

    my $row = $dbh->selectrow_arrayref(q{SELECT '10:30', :name -- not :a placeholder}, undef, name => 'Abba');
    say "@$row";    # 10:30 Abba

To use a C<?>, C<:> or C<$> that isn't a placeholder, put a backslash
before it, as DBD::Pg allows. PostgreSQL's C<?>, C<?|> and C<?&>
operators are examples. The backslash and the character after it are
passed on unchanged, and DBD::Pg removes the backslash:

    $pg->prepare(q{SELECT * FROM doc WHERE data \? 'key' AND id = :id});

=head2 Strings, by dialect

Strings are read by the rules of the handle's L<dialect|/"The dialect">:

=over 4

=item *

With C<mysql> and C<MariaDB>, a backslash escapes a character in a
string (C<'it\'s'>), C<"..."> is a string, and C<#> starts a comment.
MySQL's C<NO_BACKSLASH_ESCAPES> mode isn't noticed.

=item *

With other dialects, a backslash is an ordinary character in a
string (C<'C:\'>), except in PostgreSQL's C<E'...'> strings.

=back

To read one statement as another dialect, give it C<ekorn_dialect>:

    $dbh->prepare($statement, {ekorn_dialect => 'mysql'});

=head2 DBD::Pg's own options

DBD::Pg's placeholder options are followed, whether set on the
database handle or passed to C<prepare>:

=over 4

=item *

With C<pg_placeholder_dollaronly>, only C<$1>-style placeholders are
recognised. The statement is passed on as written, for DBD::Pg to
read and bind.

=item *

With C<pg_placeholder_nocolons>, the C<:1> and C<:name> styles aren't
placeholders, so array slices such as C<data[:2]> are left alone.

=back

=head1 3. Preparing, binding and running

The user guide's L<chapter
3|DBIx::Squirrel::Manual::HowTo/"3. Binding values and running statements">.

=head2 prepare

    $sth = $dbh->prepare($statement);
    $sth = $dbh->prepare($statement, \%attr);

Prepares a statement, with placeholders in any of the
L<styles|/"The styles">, and returns a C<DBIx::Squirrel::st>.

The statement can be:

=over 4

=item *

a string;

=item *

an array reference of lines, which are joined with spaces;

=item *

a code reference returning either;

=item *

a statement handle, whose statement is prepared again.

=back

    my $sth = $dbh->prepare(['SELECT title', 'FROM album', 'WHERE id = ?']);
    $sth->execute(1);
    say $sth->fetchrow_arrayref->[0];    # Arrival

    my $again = $dbh->prepare(sub { 'SELECT name FROM artist WHERE id = ?' });
    $again->execute(3);
    say $again->fetchrow_arrayref->[0];    # Cream

Blank space around the statement is removed. Comments are passed on to
the database.

Unlike the DBI's C<prepare>, it B<always croaks> if the statement
can't be prepared, whatever C<RaiseError> is set to. The message is the
one the DBI raises under C<RaiseError>, such as
C<DBD::SQLite::db prepare failed: near "SELEC": syntax error>.

Most statements are strings given without attributes. Such a statement
is read for placeholders once for each database handle, which keeps
what it found. The handle keeps up to 1000 statements, and starts
again when it has that many.

A statement taking a L<list|/"Lists"> can't be prepared without its
values, so C<prepare> croaks given one.

=head2 execute

    $rv = $sth->execute;
    $rv = $sth->execute(@bind_values);
    $rv = $sth->execute(\@bind_values);
    $rv = $sth->execute(%values);
    $rv = $sth->execute(\%values);

Executes the statement, as the DBI's C<execute> does, and returns what
it returns. Values given are bound first, as L<C<bind>|/"bind"> binds
them.

A statement with numbered or named placeholders, executed without
values, croaks unless each placeholder already has a value bound. The
value can come from L<C<bind>|/"bind">, L<C<bind_param>|/"bind_param"> or an
earlier C<execute>, as the DBI keeps them. The DBI would leave the
placeholder unbound, which most drivers read as C<NULL>. C<do>,
iterators and the select methods check the same way:

    my $sth = $dbh->prepare('SELECT name FROM artist WHERE id = :id');
    eval { $sth->execute };
    print $@;    # Expected a value for each placeholder (none for id) at ... line ...

    $sth->bind_param(id => 1);
    $sth->execute;
    say $sth->fetchrow_arrayref->[0];    # Abba

The DBI doesn't finish a statement still active from an earlier
C<execute> before executing it again. Nor does C<execute>, unless the
C<ekorn_finish_active> attribute is true, on the database handle or the
statement.

=head2 bind

    $sth = $sth->bind(@bind_values);
    $sth = $sth->bind(\@bind_values);
    $sth = $sth->bind(%values);
    $sth = $sth->bind(\%values);

Binds values to the statement's placeholders without executing it.
Returns the statement handle, or nothing if the DBI couldn't bind a
value. How values are matched to placeholders depends on the
L<style|/"The styles">.

    my $sth = $dbh->prepare('SELECT name FROM track WHERE plays > :plays ORDER BY plays DESC');
    $sth->bind(plays => 8000)->execute;
    say $sth->fetchrow_arrayref->[0];    # Dancing Queen

If the values don't match the placeholders, it croaks at the caller's
line:

=over 4

=item numbered

There aren't as many values as the highest number: C<Expected 2 bind values, not 1>.

=item named

There's an odd number of values: C<Expected names and values in pairs>.

=item named

A name isn't one of the statement's: C<Expected a placeholder of the statement (x)>.

=item named

A name has no value: C<Expected a value for each placeholder (none for id)>.

=back

=head2 An array reference of values

A single array reference stands for the values in it, so
C<< $sth->bind([1, 2]) >> is C<< $sth->bind(1, 2) >>. The same goes for
C<execute>, C<do> and the select methods.

There are two exceptions, each for a statement taking one value:

=over 4

=item *

To a statement whose one value is a L<list|/"Lists">, the array
reference is the list.

=item *

DBD::Pg binds an array reference as a PostgreSQL array. So, with
DBD::Pg, an array reference given to a statement taking one value,
such as C<SELECT * FROM artist WHERE id = ANY(?)>, is that value, as
it would be with the DBI. Through another driver, such as DBD::ODBC,
it's unwrapped as usual, as the driver can't bind arrays.

=back

=head2 bind_param

    $rv = $sth->bind_param($placeholder, $value);
    $rv = $sth->bind_param($placeholder, $value, \%attr);
    $rv = $sth->bind_param($placeholder, $value, $bind_type);

Binds one value, as the DBI's C<bind_param> does, and returns what it
returns. The placeholder can be given:

=over 4

=item *

by position, for C<?> placeholders, as with the DBI;

=item *

by number, for numbered placeholders, with or without the sigil: C<1>
or C<'$1'>;

=item *

by name, for named placeholders, with or without the sigil: C<'id'>
or C<':id'>;

=item *

by position, for named placeholders too, as with the DBI.

=back

The value is bound to every use of the placeholder in the statement.
The value for a L<list|/"Lists"> is the list. Each value in it is bound
to a position of its own.

    my $sth = $dbh->prepare('SELECT :a + :a, :b');
    $sth->bind_param(a => 2);
    $sth->bind_param(':b', 3);
    $sth->execute;
    say join ' ', @{ $sth->fetchrow_arrayref };    # 4 3

=head2 do

    $rv = $dbh->do($statement);
    $rv = $dbh->do($statement, \%attr, @bind_values);
    $rv = $dbh->do($statement, undef, @bind_values);
    $rv = $dbh->do($statement, @bind_values);

Runs a statement, and returns what the DBI's C<do> returns: the number
of rows affected, C<0E0> for none, or C<undef> on an error without
C<RaiseError>. An error names C<do>, as the DBI's does:
C<DBD::SQLite::db do failed: ...>.

Unlike the DBI's, the attributes may be left out. The first argument
after the statement is taken as the attributes only if it's a hash
reference or C<undef>. An array reference there stands for the L<values
in it|/"An array reference of values">. Any other reference croaks:
C<Expected a reference to a HASH or ARRAY>.

    $dbh->begin_work;
    say $dbh->do('UPDATE artist SET name = :name WHERE id = :id', name => 'BLUR', id => 2);    # 1
    say $dbh->do('UPDATE artist SET name = ? WHERE id = ?', ['Blur', 2]);                       # 1
    $dbh->rollback;

A statement with C<?> placeholders, or none, goes to the driver's own
C<do>, as with plain DBI. So the driver's row counts and options apply,
such as running several statements with DBD::SQLite's
C<sqlite_allow_multiple_statements>. A statement with numbered or named
placeholders is prepared and executed. Some drivers, such as
DBD::SQLite, then count the rows of an C<UPDATE ... RETURNING> only as
they're fetched, giving C<0E0>.

Like the DBI's, C<do> returns no rows, even from a C<SELECT> or a
C<RETURNING> clause. Use C<prepare> and C<execute>, an
L<iterator|/"4. Iterators">, or the select methods, for those.

=head2 The select methods

    @row_ary  = $dbh->selectrow_array($statement, \%attr, @bind_values, @stages);
    $ary_ref  = $dbh->selectrow_arrayref($statement, \%attr, @bind_values, @stages);
    $hash_ref = $dbh->selectrow_hashref($statement, \%attr, @bind_values, @stages);
    $ary_ref  = $dbh->selectall_arrayref($statement, \%attr, @bind_values, @stages);
    @rows     = $dbh->selectall_array($statement, \%attr, @bind_values, @stages);
    $hash_ref = $dbh->selectall_hashref($statement, $key_field, \%attr, @bind_values, @stages);
    $ary_ref  = $dbh->selectcol_arrayref($statement, \%attr, @bind_values, @stages);

Without stages, each works as the DBI's does. It prepares the
statement as C<prepare> does, unless it's already a statement handle,
and binds the values as L<C<bind>|/"bind"> binds them. C<selectall_array>
gives the rows C<selectall_arrayref> gives, as a list, as the DBI's
does.

As with L<C<do>|/"do">, the attributes may be left out. The first
argument after the statement, or after C<selectall_hashref>'s key
field, is taken as the attributes only if it's a hash reference or
C<undef>. So named values given in a hash reference, or a first value
that's C<undef>, need the attributes, or C<undef>, in front.

B<Given stages after the bind values,> each pushes what the DBI's
method returns through them, as a pipeline called with values does,
and returns what comes out of the last: every value; or, where one
value is asked for, a sink's result, if a sink is last, and otherwise
how many values came out. C<selectrow_array> pushes the row's values,
C<selectall_array> each row, and the others their one reference. As a
pushed run has no statement as its source, the stages can't use
C<pluck> by a name for an array row, or C<as_hash>.

    my @names = $dbh->selectall_array(
        'SELECT name FROM artist ORDER BY id',
        sub { $_->[0] },
        sub {uc},
    );
    say "@names";    # ABBA BLUR CREAM

    say scalar $dbh->selectall_array('SELECT * FROM artist', sub { $_->[0] > 1 ? $_ : () });    # 2

    my $col = $dbh->selectcol_arrayref('SELECT name FROM artist WHERE id IN ($1, $2) ORDER BY id', 1, 2);
    say "@$col";    # Abba Blur

Unlike C<prepare>, they don't croak if the statement can't be prepared.
Without C<RaiseError>, each returns what the DBI's returns, C<undef> or
nothing.

=head1 4. Iterators

The user guide's L<chapter
4|DBIx::Squirrel::Manual::HowTo/"4. A statement as a source of rows">.

An iterator treats a statement as a source of rows, read only as
they're wanted. Each row is run through the iterator's
L<stages|/"5. Stages and Context">, if any, and what comes out is a
result. With no stages, the result is the row.

=head2 iterate

    $it     = $dbh->iterate($statement, \%attr, @bind_values, @stages);
    $it     = $dbh->iterate($statement, @bind_values, @stages);
    $it     = $sth->iterate(@bind_values, @stages);
    @result = $dbh->iterate($statement, @bind_values, @stages, $sink);

On a database handle, C<iterate> prepares the statement, as C<prepare>
does, and returns a C<DBIx::Squirrel::Iterator> over its results. As
with C<do>, the attributes may be left out. On a statement handle, it
returns an iterator over that statement's results.

The bind values are in any form C<execute> takes. The B<stages> are at
the end of the arguments: code references, pipelines, or any of
Ekorn::Pipeline's stages. Each row is run through them, in order. See
L<Stages|/"Stages">.

B<A sink given last says what comes back.> If the last stage is one
of Ekorn::Pipeline's L<sinks|/"8. Sinks">, C<iterate> reads the run to its
end and returns the sink's result, not an iterator.

    my $it = $dbh->iterate('SELECT name FROM artist WHERE name LIKE :pattern ORDER BY id', pattern => '%r%', sub { $_->[0] });
    while (my($name) = $it->next) {
        say $name;
    }
    # Blur
    # Cream

The statement isn't executed until the first result is asked for. It's
finished when the results run out, when the run is ended early, by a
L<stop|/"6. Stopping a pipeline">, or by C<first> or C<single>, and when
the iterator is let go.

=head2 How rows are fetched

Rows are fetched with the DBI's C<fetchall_arrayref>, 2 at first, the
least that tells whether there's a second, then twice as many each
time a fetch fills its batch, up to 64. So reading one row fetches no
more than two, and a large result is never held all at once.

Without stages, C<all> takes what's left of the batch and fetches the
rest at once. That's nearly as quick as the DBI's own
C<selectall_arrayref>. With stages, each row goes through them in turn,
which costs a little for each row. So to change every row of a large
result, when nothing needs to stop early, C<map> over C<all> is quicker
than a stage:

    my @names = map { $_->[0] } $dbh->iterate('SELECT name FROM artist ORDER BY id')->all;
    say "@names";    # Abba Blur Cream

=head2 The iterator's methods

=over 4

=item C<next>

Returns the next result, or an empty list when there are no more.

=item C<all>

Returns the results still to come, reading the run to its end: as a list, or, asked for one value, an array reference of them, never a count. The statement is then finished. Without stages, it fetches the rest at once.

=item C<first>

Returns the next result, or C<undef> if there's none, and finishes the statement.

=item C<single>

Returns the next result, or C<undef> if there's none, and finishes the statement. If there's another, it warns, C<Expected only one item, but there were more>, and returns the first: for a statement that lost its C<LIMIT 1>.

=item C<ended>

Returns how the last run ended: C<done>, C<stopped> or C<died>; nothing while a run is going, or before one has started.

=item C<reset>

Runs the statement again, from its first row, and returns the iterator. See L<reset|/"reset">.

=item C<column_names>

Returns the names of the statement's columns, as C<fetchrow_hashref> would key them, following C<FetchHashKeyName>. They're read when the statement is executed, as DBD::mysql gives none once the last row is fetched.

=item C<sth>

Returns the statement handle. It changes when C<reset> prepares a statement taking a list again.

=back

A stage can return C<undef> as a result. So read C<next> in list
context, as below, rather than testing whether what it returns is
defined. C<all>, C<first> and C<single> take what's left of the run, so
after C<next> they start from the next result:

    my $it = $dbh->iterate('SELECT name FROM artist ORDER BY id', sub { $_->[0] });
    my($abba) = $it->next;
    say $abba;                  # Abba
    say join ' ', $it->all;     # Blur Cream
    say $it->ended;             # done

    say $dbh->iterate('SELECT name FROM artist ORDER BY id', sub { $_->[0] })->first;    # Abba
    say $dbh->iterate('SELECT COUNT(*) FROM track', sub { $_->[0] })->single;          # 6
    say join ', ', $dbh->iterate('SELECT id, title AS Album FROM album')->column_names;    # id, Album

C<ended> is C<done> when the rows ran out, C<stopped> when the run was
cut short, by C<first>, by C<single> finding a second result, or by a
stage that stopped, and C<died> when a stage died. A run read with C<|>
or C<@{}> is the iterator's last run too (see L<11.
Operators|/"11. Operators: E<verbar> and @{}">).

=head2 reset

    $it = $it->reset;
    $it = $it->reset(@bind_values, @stages);

Executes the statement again, ready to iterate from its first row, and
returns the iterator. If the statement is still active, it's finished
first, and whatever the run before held goes with it. Bind values
given replace those given before. Stages given are added to those
given when the iterator was made. Both are kept until others are
given:

    my $it = $dbh->iterate('SELECT name FROM artist WHERE id > ? ORDER BY id', 0, sub { $_->[0] });
    say join ' ', $it->all;                      # Abba Blur Cream
    say join ' ', $it->reset(1)->all;            # Blur Cream
    say join ' ', $it->reset(sub {lc})->all;     # blur cream

A statement taking a L<list|/"Lists"> is prepared again, on a new
statement handle, if a list given has a different number of values
from the one before. C<sth> then returns the new handle.

=head2 Rows as arrays or hashes

Rows are fetched as arrays, unless the C<ekorn_slice> attribute says
otherwise. It's a slice as the DBI's C<fetchall_arrayref> takes it: an
array reference for arrays, or a hash reference for hashes. Given to
C<connect>, it's the default for each statement the handle prepares.
Given to C<prepare> or C<iterate>, it's for that statement.

    my $it = $dbh->iterate('SELECT id, name FROM artist ORDER BY id', {ekorn_slice => {}}, sub { "$_->{id}: $_->{name}" });
    say join ', ', $it->all;    # 1: Abba, 2: Blur, 3: Cream

=head2 One iterator to a statement handle

A statement handle can have only one iterator going through its
results at a time. While the first has results left, executing another
over the same handle croaks:
C<Expected the statement handle's other iterator to be finished>. Read
the first to the end, or let it go out of scope, first. An iterator
that's let go ends its run, and finishes its statement.

=head1 5. Stages and Context

The user guide's L<chapter
5|DBIx::Squirrel::Manual::HowTo/"5. Stages: shaping rows on the way out">.

=head2 Stages

A stage is given one value, as its argument and in C<$_>, and returns a
list. Write it whichever way reads best: name the value with a
signature, or leave the signature out and use C<$_>:

    sub ($row) { $row->[1] }    # the value, named
    sub { $_->[1] }             # the same, in $_

C<$_> is localised for each call, so your own C<$_> is unchanged.

=over 4

=item nothing

B<It's a:> filter

B<The value:> is dropped.

=item one value

B<It's a:> map

B<The value:> is replaced by that value, which goes on.

=item several values

B<It's a:> flatMap

B<The value:> is replaced by each, which goes through the rest of the stages on its own.

=back

Each value goes through every stage before the next one starts. So the
values come out in order. A stage returns whatever its last statement
gives, so a stage run for its side effects should still return what
the next stage needs.

    my @words = $dbh->iterate(
        'SELECT title, year FROM album ORDER BY year',
        sub { $_->[1] < 1990 ? $_ : () },    # filter
        sub { split ' ', $_->[0] },          # flatMap
        sub {lc},                            # map
    )->all;
    say "@words";    # disraeli gears arrival

A stage can be a code reference, a L<pipeline|/"10. Pipelines">, or one
of Ekorn::Pipeline's stage objects, such as those its words and the
canned stages make. L<How values go through
stages|Ekorn::Pipeline::Manual::Reference/"How values go through stages">,
in Ekorn's reference, has the details.

=head2 Context

DBIx::Squirrel::Context's functions tell a stage what it can't work
out from its value. None is exported by default.

    use DBIx::Squirrel::Context qw(iterator result_number result_original);

=over 4

=item C<iterator>

The iterator running the stage, in its own stages. Its C<sth> is the statement handle, and the statement handle's C<Database> is the database handle.

=item C<result_number>

The number of the result being made, from 1. It counts results, not rows. While a stage drops rows, the number stays the same. Each value a stage returns in place of one row is a result of its own. In a flush, it's the number of the first value the flush returns.

=item C<result_original>

The row the result is being made from, as it was fetched, before any stage changed it. For a result set, it's the row object. In a L<flush|/"7. Gathering: stages made for each run">, and the stages after it, it's C<undef>: what a flush gives comes from every row, not one.

=back

C<result_original> works in any run reading a statement: an iterator's
or result set's own stages, and the stages of a chain made with C<|>,
or of a pipeline of yours, reading one, as it's read from the L<run's
context|/"The run's context">. C<result_number> and C<iterator> work only
in an iterator's or result set's own stages, run by its C<next>, C<all>,
C<first> or C<single>, or by a sink given last to the call that made it.
Elsewhere, and outside a stage, they return C<undef>.

    my @chart = $dbh->iterate(
        'SELECT name, plays FROM track ORDER BY plays DESC',
        sub { $_->[0] },
        sub { result_number() . ". $_ (" . result_original()->[1] . ')' },
    )->all;
    say $chart[0];    # 1. Dancing Queen (9100)

=head2 Canned stages

Four modules of ready-made stages ship with DBIx::Squirrel, each for
one kind of job. Each exports the stages it's usually used for, and
the rest on request. C<:all> gives them all, and C<()> none. Naming a
stage in the import list replaces the defaults. To have the defaults
and one more, name C<:DEFAULT> too:

    use DBIx::Squirrel::Stages::Flow qw(:DEFAULT take_while);

=over 4

=item C<DBIx::Squirrel::Stages::Flow>

B<Exported by default:> C<take($n)>, C<drop($n)>

B<On request:> C<take_first>, C<take_last>, C<take_single>, C<take_while { ... }>, C<drop_while { ... }>, C<take_if { ... }>, C<drop_if { ... }>

=item C<DBIx::Squirrel::Stages::Rows>

B<Exported by default:> C<pluck($column)>, C<as_hash>

=item C<DBIx::Squirrel::Stages::Batch>

B<Exported by default:> C<batch($n)>, C<collect>, C<collect { ... }>

=item C<DBIx::Squirrel::Stages::Taps>

B<Exported by default:> C<peek { ... }>, C<count_into(\$n)>

B<On request:> C<dump_to($fh)>

=back

Flow's are described in L<6. Stopping a
pipeline|/"6. Stopping a pipeline">, and Batch's in L<7.
Gathering|/"7. Gathering: stages made for each run">. Flow's, Batch's and
Taps' stages are Ekorn::Pipeline's, exported from a list of
DBIx::Squirrel's own; its reference's L<Canned
stages|Ekorn::Pipeline::Manual::Reference/"Canned stages">
describes them in full. Rows' stages are DBIx::Squirrel's own. Each is
a function that makes a stage, checking what it's given when it's
called, not on each value.

=over 4

=item C<pluck($column)>

Gives one column of each row, by its name, in any case, or its position, from 0, whether the row is an array, a hash or a row object.

=item C<as_hash>

Gives each row as a hash, as C<fetchrow_hashref> would, keyed as C<FetchHashKeyName> says. A hash row is passed on unchanged.

=item C<peek { ... }>

Calls the block with each value, and passes the value on.

=item C<count_into(\$n)>

Counts the values into C<$n>, from 0 on each run, and passes them on.

=item C<dump_to($fh)>

Writes each value, with Data::Dumper, to C<$fh> or STDERR, and passes it on.

=back

    my $read  = 0;
    my @names = $dbh->iterate(
        'SELECT id, name FROM artist ORDER BY id',
        count_into(\$read),
        pluck('name'),
    )->all;
    say "@names, from $read rows";    # Abba Blur Cream, from 3 rows

    my $album = $dbh->iterate('SELECT title, year FROM album WHERE id = 2', as_hash)->first;
    say "$album->{title} ($album->{year})";    # Parklife (1994)

C<pluck> and C<as_hash> find the column names in the L<run's
context|/"The run's context">, which a statement gives it: an iterator's
or result set's own stages, or a chain made with C<|>, or a pipeline of
yours, reading one. So a name for an array row, or C<as_hash>, needs a
statement to be what the run reads. C<pluck> by name for a hash row
reads the hash's own keys, and works anywhere.

**C<pluck> reads the statement's columns, not the row's.** After a
stage that reshapes rows, a name or position for an array row picks
the wrong field, and says nothing. Make the rows hashes first, with
C<as_hash>. Then C<pluck> by name reads each hash's own keys:

    my $sql = 'SELECT id, name FROM artist ORDER BY id';

    my @wrong = $dbh->iterate(
        $sql,
        sub { [reverse @$_] },
        pluck('id'),
    )->all;
    say "@wrong";    # Abba Blur Cream

    my @ids = $dbh->iterate(
        $sql,
        as_hash,
        sub { +{%$_, name => uc $_->{name}} },
        pluck('id'),
    )->all;
    say "@ids";    # 1 2 3

C<dump_to> is for debugging. It writes each value in full, secrets and
all. It doesn't escape control characters in strings, so a value from
outside can send escape sequences to a terminal.

=head1 6. Stopping a pipeline

The user guide's L<chapter 6|DBIx::Squirrel::Manual::HowTo/"6. Stopping early">.

=head2 Stop

    use DBIx::Squirrel::Stop;

    Stop();
    Stop(@values);
    Ekorn::Pipeline::Stop->throw(@values);

Called from a stage, C<Stop> ends the run early and quietly:

=over 4

=item *

The rest of that stage doesn't run.

=item *

The values already out of the pipeline are kept.

=item *

Any values the stop carries go on through the stages after it.

=item *

Nothing else is processed, and no more rows are fetched.

=back

An iterator that's stopped finishes its statement. Stages after the
one that stopped, made with
L<C<gather>|/"7. Gathering: stages made for each run">, still have their
flushes called.

    my @upto = $dbh->iterate(
        'SELECT title, year FROM album ORDER BY year',
        sub { $_->[1] >= 1990 ? Stop($_) : $_ },    # this one, then no more
        sub { $_->[0] },
    )->all;
    say "@upto";    # Disraeli Gears Arrival Parklife

C<Stop> is exported by default. C<< Ekorn::Pipeline::Stop->throw(@values) >>
does the same without importing it. To keep C<Stop> out of your
namespace, C<use DBIx::Squirrel::Stop ()>.

=head2 What a stop is

A stop is an exception, an C<Ekorn::Pipeline::Stop>, which the pipeline
catches. DBIx::Squirrel::Stop isn't a class: it exports Ekorn's
C<Stop>. A subclass of your own is a subclass of
C<Ekorn::Pipeline::Stop>, and stops a pipeline as C<Stop> does. Ekorn's
reference says what a stop holds, in L<The stop
object|Ekorn::Pipeline::Manual::Reference/"The stop object">.

A stage that catches errors itself, with C<eval> or C<try>, should throw
a stop on again. Check for C<Ekorn::Pipeline::Stop>. Every stop is one,
including those the canned stages throw, such as C<take>'s:

    use experimental qw(try);

    my @safe = $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        sub ($row) {
            try {
                Stop() if $row->[0] eq 'Cream';
                return uc $row->[0];
            }
            catch ($e) {
                die $e if $e isa 'Ekorn::Pipeline::Stop';
                return 'unknown';
            }
        },
    )->all;
    say "@safe";    # ABBA BLUR

=head2 Taking and dropping

DBIx::Squirrel::Stages::Flow's stages decide which values go on, by
their place or by a test:

=over 4

=item C<take($n)>

Passes on the first C<$n> values, then stops the run, so no more rows are fetched.

=item C<drop($n)>

Drops the first C<$n> values, and passes on the rest.

=item C<take_first>

Passes on the first value, then stops the run: C<take(1)>.

=item C<take_last>

Passes on the last value, once there are no more, reading every one to find it; nothing if there were none.

=item C<take_single>

Passes on the one value. At a second, it warns, C<Expected only one item, but there were more>, and stops the run, so only the first goes on.

=item C<take_while { ... }>

Passes on values while the block is true of them. At the first it's false of, it stops the run, and doesn't pass that value on.

=item C<drop_while { ... }>

Drops values while the block is true of them, then passes on the rest, from the first it's false of.

=item C<take_if { ... }>

Passes on each value the block is true of, testing every one, as C<grep> does; it never stops the run.

=item C<drop_if { ... }>

Passes on each value the block is false of, testing every one.

=back

    my @page = $dbh->iterate(
        'SELECT name FROM track ORDER BY id',
        sub { $_->[0] },
        drop(2),
        take(2),
    )->all;
    say join ', ', @page;    # Girls & Boys, Parklife

    my @hits = $dbh->iterate(
        'SELECT name, plays FROM track ORDER BY plays DESC',
        take_while { $_->[1] > 6000 },
        sub { $_->[0] },
    )->all;
    say join ', ', @hits;    # Dancing Queen, Sunshine of Your Love, Girls & Boys

    my @newest = $dbh->iterate(
        'SELECT title FROM album ORDER BY year',
        take_last,
        sub { $_->[0] },
    )->all;
    say "@newest";    # The Great Escape

    my @popular = $dbh->iterate(
        'SELECT name, plays FROM track ORDER BY id',
        take_if { $_->[1] > 6000 },
        sub { $_->[0] },
    )->all;
    say join ', ', @popular;    # Dancing Queen, Girls & Boys, Sunshine of Your Love

In SQL, C<LIMIT> and C<OFFSET> page results in the database, which is
quicker. C<take> and C<drop> are for when a stage in Perl decides which
rows go on.

=head1 7. Gathering: stages made for each run

The user guide's L<chapter 7|DBIx::Squirrel::Manual::HowTo/"7. Parts made for each run">.

=head2 gather

    use DBIx::Squirrel::Gather;

    my $stage = gather { ...; return $step };
    my $stage = gather { ...; return ($step, $flush) };
    my $stage = gather { ...; return ($step, $flush, $end) };
    my $stage = gather { ...; return {step => $step, flush => $flush, end => $end} };

C<gather> makes a stage afresh at the start of each run, by calling its
block, so whatever the block declares is fresh each time. A run is
each execution of an iterator or result set, including after C<reset>,
each call of a Sugar statement, and each call of a pipeline. The block
returns:

=over 4

=item *

B<the step:> a code reference, called with each value as any stage
is, or a pipeline, whose stages are made for the run in its place;

=item *

B<optionally, the flush:> called with no arguments once the values
run out, even if there were none. What it returns goes through the
rest of the stages, as what a stage returns does. After a
L<stop|/"6. Stopping a pipeline">, only the flushes of the stages after
the one that stopped are called;

=item *

B<optionally, the end:> called once the run has ended, however it
ended, and told how: C<done>, C<stopped> or C<died>. An iterator's run
is C<done> once its rows run out, and C<stopped> when C<first> or
C<single> finishes it. What the end returns is dropped.

=back

The parts can be given as a list, in that order, with C<undef> for a
flush left out before an end, or by name, as one hash reference with
the keys C<step>, C<flush> and C<end>, giving only those the stage has.

    # Each value, then, once they run out, how many there were
    sub and_count () {
        return gather {
            my $count = 0;    # this run's
            return (sub ($value) { $count++; $value }, sub () {"($count)"});
        };
    }

    my $it = $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        sub { $_->[0] },
        and_count,
    );
    say join ' ', $it->all;           # Abba Blur Cream (3)
    say join ' ', $it->reset->all;    # Abba Blur Cream (3)

    my @how;
    my $watched = gather { +{step => sub { $_->[0] }, end => sub ($how) { push @how, $how }} };
    $dbh->iterate('SELECT name FROM artist', $watched)->first;
    say "@how";    # stopped

A block that returns anything else croaks as the run starts:
C<Expected stage #%s, made with gather, to return a code reference or a pipeline, and optionally a flush and an end>.
C<gather> given something other than a block or code reference croaks
C<Expected a code reference>. Ekorn's reference gives the order flushes
and ends are called in, in L<Flushes and
ends|Ekorn::Pipeline::Manual::Reference/"Flushes and ends">.

A stage made with C<gather> is an C<Ekorn::Pipeline::Gather>, an object
that can go wherever a stage can. C<gather> is exported by default; to
keep it out of your namespace, C<use DBIx::Squirrel::Gather ()>.

=head2 Batching and collecting

DBIx::Squirrel::Stages::Batch's stages are made with C<gather>:

=over 4

=item C<batch($n)>

Passes values on in batches of C<$n>, each an array. The last, shorter batch comes when the values run out.

=item C<collect>

Holds every value. When they run out, it passes on an array of them.

=item C<collect { ... }>

Holds every value. When they run out, it passes on what the block makes of them, given as its arguments.

=back

    my @batches = $dbh->iterate(
        'SELECT name FROM track ORDER BY id',
        pluck('name'),
        batch(4),
    )->all;
    say scalar(@$_), ': ', join ', ', @$_ for @batches;
    # 4: Dancing Queen, Knowing Me, Knowing You, Girls & Boys, Parklife
    # 2: Country House, Sunshine of Your Love

    say $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        pluck('name'),
        collect { join '+', @_ },
    )->first;
    # Abba+Blur+Cream


=head1 8. Sinks

The user guide's L<chapter
8|DBIx::Squirrel::Manual::HowTo/"8. Sinks: saying what you want back">.

A sink is a last stage that says what a run gives. Given last to
C<iterate>, C<results>, a Sugar function, or a select method, it makes
the call read the run through and give the sink's result, not an
iterator. The sinks are Ekorn::Pipeline's, from
Ekorn::Pipeline::Sinks, which exports none by default, and
DBIx::Squirrel::Tooling's C<:sinks> exports them all:

    use Ekorn::Pipeline::Sinks qw(keep_all keep_first keep_last keep_single keep count_items to_file to_fh);

=over 4

=item C<keep_all>

B<Gives:> every result, as a list; or, where one value is asked for, an array reference of them

B<Stops the run early?:> no

=item C<keep_first>

B<Gives:> the first result, or C<undef> if none

B<Stops the run early?:> yes

=item C<keep_last>

B<Gives:> the last result, reading every one to find it, or C<undef> if none

B<Stops the run early?:> no

=item C<keep_single>

B<Gives:> the one result, or C<undef> if none; at a second, a warning, C<Expected only one item, but there were more>, and the first

B<Stops the run early?:> at a second

=item C<keep($n)>

B<Gives:> the first C<$n> results, as a list, or an array reference where one value is asked for

B<Stops the run early?:> yes, at C<$n>

=item C<count_items>

B<Gives:> how many results there were

B<Stops the run early?:> no

=item C<to_file($path)>

B<Gives:> writes each result to the file, a line each, and gives how many; it closes the file however the run ends

B<Stops the run early?:> no

=item C<to_fh($fh)>

B<Gives:> prints each result to your filehandle, a line each, and gives how many; you close it

B<Stops the run early?:> no

=back

A sink of many, C<keep_all> or C<keep>, never gives a count: for that,
use C<count_items>. An empty result is an empty array reference, which
is true, so test it with C<@$rows>.

    my @names = $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        pluck('name'),
        keep_all,
    );
    my $names = $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        pluck('name'),
        keep_all,
    );
    say "@names";            # Abba Blur Cream
    say scalar @$names;      # 3

    say $dbh->iterate(
        'SELECT name FROM track ORDER BY plays',
        pluck('name'),
        keep_last,
    );
    # Dancing Queen

    say $dbh->iterate(
        'SELECT name FROM artist WHERE id = ?', 2,
        pluck('name'),
        keep_single,
    );
    # Blur

    say join ', ', $dbh->iterate(
        'SELECT name FROM track ORDER BY plays DESC',
        pluck('name'),
        keep(2),
    );
    # Dancing Queen, Sunshine of Your Love

    say $dbh->iterate('SELECT * FROM album', count_items);    # 4

The iterator's methods and the sinks overlap: C<all> and C<keep_all>,
C<first> and C<keep_first>, C<single> and C<keep_single>. A method takes
what's left of an iterator you have; a sink says, in the call, what it
gives, and is the only way to have a count, the last, the first few,
or a file. C<all> without stages is quicker than C<keep_all>, as it
fetches every row in one go.

Ekorn's reference has the sinks in full, and how to write one, in
L<Sinks|Ekorn::Pipeline::Manual::Reference/"Sinks: Ekorn::Pipeline::Sinks">.

=head1 9. Result sets and row objects

The user guide's L<chapter 9|DBIx::Squirrel::Manual::HowTo/"9. Rows as objects">.

=head2 results

    $results = $dbh->results($statement, \%attr, @bind_values, @stages);
    $results = $dbh->results($statement, @bind_values, @stages);
    $results = $sth->results(@bind_values, @stages);
    @result  = $dbh->results($statement, @bind_values, @stages, $sink);

As L<C<iterate>|/"iterate">, returning a C<DBIx::Squirrel::Results>, or a
sink's result, if the last stage is a sink. A result set is an
iterator whose rows are objects, with a method for each column, named
in lower case. The stages see the objects. A result set has the
iterator's methods, and no others.

    my $results = $dbh->results('SELECT id, Name FROM artist WHERE id <= ? ORDER BY id', 2);
    while (my($artist) = $results->next) {
        say $artist->id, ' ', $artist->name;
    }
    # 1 Abba
    # 2 Blur

Rows are always fetched as arrays for a result set. The C<ekorn_slice>
attribute doesn't apply.

=head2 Row objects

Each row is an array, blessed into a class with a method for each
column. There's one class for each base class and list of column
names. It's made the first time a result set fetches rows with those
columns, and kept for the life of the program. A row needs nothing
from its result set, and can be kept after the result set has gone.

A column gets no method:

=over 4

=item *

if its name can't be a method's, such as C<COUNT(*)>;

=item *

if the base class already has a method of that name, such as C<can>,
C<isa>, C<get_column>, or one of your own.

=back

When two columns have one name, as in C<SELECT a.id, b.id>, the method
is the first's. To give such a column a method, give it another name
in the statement, with C<AS>:

    my $row = $dbh->results('SELECT COUNT(*), COUNT(*) AS albums FROM album')->first;
    say $row->albums;    # 4
    say $row->[0];       # 4

=head2 get_column

    $value = $row->get_column($name);
    $value = $row->get_column($position);

Returns a column's value by its name, in any case, or by its position,
from 0. It reaches every column, including those without a method. It
croaks if the row has no such column:
C<Expected a column of the row (x)>.

    my $row = $dbh->results('SELECT COUNT(*) FROM album')->first;
    say $row->get_column('count(*)');    # 4
    say $row->get_column(0);             # 4

=head2 Methods of your own

Row classes are subclasses of C<DBIx::Squirrel::Result>, or of the
class given in the C<ekorn_result_class> attribute, which must itself
be a subclass of C<DBIx::Squirrel::Result>. So rows can have methods of
your own:

    package My::Artist {
        our @ISA = 'DBIx::Squirrel::Result';
        sub shout ($self) { return uc $self->name }
    }

    my $artist = $dbh->results('SELECT * FROM artist WHERE id = 2', {ekorn_result_class => 'My::Artist'})->first;
    say $artist->shout;    # BLUR

A class that isn't a subclass of C<DBIx::Squirrel::Result> croaks:
C<Expected ekorn_result_class to be a subclass of DBIx::Squirrel::Result (My::Other)>.

=head1 10. Pipelines

The user guide's L<chapter
10|DBIx::Squirrel::Manual::HowTo/"10. Building pipelines from pipelines">.

The pipeline is
L<Ekorn::Pipeline|Ekorn::Pipeline>'s. It
began here, and is now a distribution of its own, so that any function
can take stages from its caller. DBIx::Squirrel uses it as it is: a
pipeline is made with C<< Ekorn::Pipeline->new >>, and the handles' C<pipe>
and C<tap> are Ekorn::Pipeline::Pipes'. Loading it doesn't load the
DBI, so a pipeline works in code that has nothing to do with a
database.

DBIx::Squirrel keeps its own names for the modules of functions:
C<DBIx::Squirrel::Stop>, C<DBIx::Squirrel::Gather>, and the stages in
C<DBIx::Squirrel::Stages::Flow>, C<Batch> and C<Taps>. Each exports
Ekorn's functions from a list of DBIx::Squirrel's own, so a function
added to Ekorn::Pipeline reaches DBIx::Squirrel's modules only once
it's added to that list, and documented here. The objects are Ekorn's:
a stop is an C<Ekorn::Pipeline::Stop>, and a stage made with C<gather>
an C<Ekorn::Pipeline::Gather>. DBIx::Squirrel subclasses none of
Ekorn's classes.

Ekorn::Pipeline's
L<reference|Ekorn::Pipeline::Manual::Reference>
describes the pipeline in full, and its L<user
guide|Ekorn::Pipeline::Manual::HowTo>
has recipes for any values. This chapter keeps to what DBIx::Squirrel
does with it.

=head2 Making and running a pipeline

    use Ekorn::Pipeline;

    my $p       = Ekorn::Pipeline->new(@stages);
    my @results = $p->(@values);              # push: values in, a list out
    my $next    = $p->iterator($source);      # pull: one value per call
    my @stages  = $p->stages;

A pipeline is an object that can be called as a code reference. Called
with values, it returns what comes out of the last stage: every value
in list context; in scalar context, a sink's result, if a sink is
last, or how many values came out. C<iterator> returns an iterator, an
object called as a code reference, handing out those values one per
call, from a source; a DBIx::Squirrel iterator is a source (L<15.
Protocols|/"The iterator as a source">). C<stages> returns the
pipeline's stages, in order, a pipeline given as a stage appearing as
the stages it was made of.

    use Ekorn::Pipeline;

    my $shout = Ekorn::Pipeline->new(
        sub {uc},
        sub {"$_!"},
    );
    say join ' ', $shout->('hello', 'world');    # HELLO! WORLD!

    my $next  = Ekorn::Pipeline->new(sub { $_->[0] })->iterator($dbh->iterate('SELECT name FROM artist ORDER BY id'));
    my @names;
    while (my($name) = $next->()) { push @names, $name }
    say "@names";    # Abba Blur Cream

=head2 A pipeline as a stage

A pipeline can go wherever a stage goes: in another pipeline, or given
to C<iterate>, C<results>, an iterator's C<reset>, C<pipe>, C<tap>, a
select method, or a Sugar function, for a database or a statement. Its
stages run in its place, as if written out there, so a C<take> inside
it limits the whole run:

    use Ekorn::Pipeline;

    my $hits = Ekorn::Pipeline->new(
        sub { $_->[1] >= 5000 ? $_ : () },
        pluck('name'),
    );
    my $sql  = 'SELECT name, plays FROM track ORDER BY plays DESC';
    say join ', ', $dbh->iterate($sql, $hits)->all;             # Dancing Queen, Sunshine of Your Love, Girls & Boys, Parklife
    say join ', ', $dbh->iterate(
        $sql,
        $hits,
        take(1),
    )->all;
    # Dancing Queen


Make a stage that counts or remembers with
L<C<gather>|/"7. Gathering: stages made for each run">. A plain closure is
the same code reference wherever it goes, so its state is shared by
every run it's in.

=head2 Named pipelines

    Ekorn::Pipeline->named($name => @stages);
    use Ekorn::Pipeline::Factories qw(pipeline);
    my $p = pipeline($name, @more_stages);

C<< Ekorn::Pipeline->named >> names a pipeline for the rest of the program,
in the package that names it, unless the name is qualified, as
C<My::Module::clean>. C<pipeline>, from Ekorn::Pipeline::Factories,
makes a pipeline of stages and names, looked up in its caller's
package as it's made. A name given alone gives the pipeline named, so
its stages are numbered where it stands. The L<Sugar's
definitions|/"statement"> take names too. Ekorn's reference has the
rules, in L<Named
pipelines|Ekorn::Pipeline::Manual::Reference/"Named pipelines">.

    use Ekorn::Pipeline;

    Ekorn::Pipeline->named(first_column => sub { $_->[0] });
    say join ' ', $dbh->iterate('SELECT name FROM artist ORDER BY id', pipeline('first_column', take(2)))->all;    # Abba Blur

=head2 pipe and tap

    @results = $dbh->pipe(@stages);
    $result  = $dbh->pipe(@stages);
    $dbh     = $dbh->tap(@stages);

Database and statement handles both have these methods, from
Ekorn::Pipeline::Pipes. C<pipe> runs the handle itself through stages,
and returns what comes out of the last one: all of it in list context;
in scalar context, the first value, or C<undef>. With no stages, it
returns the handle. C<tap> runs the handle through stages for their
side effects, drops what comes out, and returns the handle however
they end, so a chain of method calls can carry on. On a statement
handle, the statement handle goes through the stages instead.

    my @names = $dbh->pipe(
        sub ($dbh) { @{ $dbh->selectcol_arrayref('SELECT name FROM artist ORDER BY id') } },
        sub {uc},
    );
    say "@names";    # ABBA BLUR CREAM

    my $n = $dbh->tap(sub ($dbh) { say 'tapped ', ref $dbh })->selectrow_array('SELECT COUNT(*) FROM artist');
    say $n;
    # tapped DBIx::Squirrel::db
    # 3

L<pipe and
tap|Ekorn::Pipeline::Manual::Reference/"pipe and tap: Ekorn::Pipeline::Pipes">,
in Ekorn's reference, says how to give a class of your own the same.

=head2 When a stage dies

If a stage dies, the call that asked for the result croaks, at your
line. The message names the stage by its place, from C<#1>, and indents
the stage's own message below. A stage inside a pipeline given as a
stage is named by its place in each: C<#2.3> is the third stage of the
pipeline given as stage #2. A stage of a named pipeline gives the name
and its place there too: C<#2.2 (main::fussy#2)>. An exception object
is passed on unchanged.

    my $it = $dbh->iterate(
        'SELECT name FROM artist',
        sub {$_},
        sub { die "no names today\n" },
    );
    eval { $it->next };
    print $@;
    # Pipeline stage #2 failed at ... line ...:
    #     no names today

    say $it->ended;    # died
    say scalar(() = $it->next);    # 0

Once a stage dies, its run has ended. An iterator then returns nothing
more: C<next> returns an empty list on every call after, and C<all>
returns nothing. No more rows are fetched, no flush is called, and the
statement is finished. An end is still called, told C<died>. C<reset>
runs the statement again, from the start. To pass over a value a stage
can't handle, the stage catches its own error and returns nothing for
it, as L<What a stop is|/"What a stop is"> shows.

=head1 11. Operators: | and @{}

The user guide's L<chapter 11|DBIx::Squirrel::Manual::HowTo/"11. Chaining with E<verbar> and @{}">.

    use Ekorn::Pipeline::Operators;

    $result = $it | @stages... | $sink;
    $chain  = $it | $stage;
    @values = @$it;

An iterator, and so a result set, overloads C<|> and C<@{}> with
Ekorn::Pipeline::Operators' C<chain> and C<drain>, as Ekorn's own
sources do. They're in force only where
C<use Ekorn::Pipeline::Operators> is in scope. Elsewhere, both croak:
C<Expected use Ekorn::Pipeline::Operators in scope, for |>.
DBIx::Squirrel loads Operators with an empty import list, so it's
there, but in force only where you say.

=over 4

=item *

C<$it | $stage> gives a chain: the iterator's results through the
stage, which C<|> can extend, and which is a source.

=item *

C<$it | ... | $sink> gives the sink's result.

=item *

C<@$it>, or C<@{ $chain }>, gives every result.

=back

**C<|> always gives one value.** Perl calls an operator for one value,
so a chain ending in C<keep_all> gives an array reference, even
assigned to an array: C<my @rows = $it | keep_all> has one element. Use
C<@{ $it | keep_all }>, or give the stages and sink to C<iterate> as
arguments.

B<Each use is a run of its own,> from the first row, through the
iterator's stages. So C<< $it->[0] >>, C<scalar @$it> and C<$#$it> read every
row to give one row, a count or an index; two uses run the statement
twice; and C<for (@$it)> reads every row before the loop starts.

B<The run it starts is the iterator's.> It ends a run the iterator
had going, so C<next> returns nothing after, and C<ended> says how the
C<|> or C<@{}> run ended, until C<reset>.

    use Ekorn::Pipeline::Operators;

    my $it    = $dbh->iterate('SELECT name FROM artist ORDER BY id', pluck('name'));
    my $names = $it | keep_all;
    say "@$names";                  # Abba Blur Cream
    say $it | count_items;          # 3
    say "@$it";                     # Abba Blur Cream
    say "@{ $it | sub {lc} }";      # abba blur cream

    my @one = $it | keep_all;
    say scalar @one;                # 1

A chain run only for its sink's effect, written as a statement of its
own, runs, but Perl warns "Useless use of numeric bitwise or (|) in
void context" as it compiles the line, before any operator is called.
Keep the result: C<my $n = $it | to_file($path)>.

=head1 12. Sugar: a function for each database and statement

The user guide's L<chapter
12|DBIx::Squirrel::Manual::HowTo/"12. A function for each database and statement">.

C<DBIx::Squirrel::Sugar> gives each database a name. The package that
names it gets a function of that name, which returns the database
handle or runs a statement on it. A statement gets a function too,
which runs it with the bind values and any stages given.

=head2 Defining them on use

    use DBIx::Squirrel::Sugar database => {
        music => [$data_source, $username, $password, \%attr],
    };
    use DBIx::Squirrel::Sugar statement => {
        artist_names => [music => 'SELECT name FROM artist', sub ($row) { $row->[0] }],
        artist       => [music => 'SELECT * FROM artist WHERE id = :id'],
    };
    use DBIx::Squirrel::Sugar qw(database statement);

Given a hash reference after C<database> or C<statement>, C<use> defines
each database or statement named in it, with its arguments in an array
reference. It gives the package each function while the package is
compiled, so the function can be called without parentheses. The
arguments are worked out then too: the environment, literals, and what
a C<BEGIN> block has set are there, but a variable the program sets as
it runs is not yet. C<use> also gives the package the C<database> and
C<statement> functions, and, given just their names, only those.

=head2 database

    $dbh      = database($name);
    $function = database($name, @connect_args);

Given a name, returns the handle of the database defined by that name,
anywhere in the program, connecting to it if it isn't connected. Given
a name and the arguments C<connect> takes, it defines a database by
that name, gives the calling package a function of that name, and
returns the function. A database defined with a database handle, in
place of a data source, is a clone of it, as C<connect> makes, made
when the database is first used. A database is defined once in a
program, by a name that can be a function's, which the package hasn't
a function of already.

=head2 The function a database is given

    $dbh     = music();
    $sth     = music($statement, @bind_values);
    $sth     = music($statement, \%attr, @bind_values);
    $it      = music($statement, @bind_values, @stages);
    @results = music($statement, @bind_values, @stages, $sink);

=over 4

=item nothing

returns the database handle.

=item a statement and bind values

prepares the statement, executes it, and returns the statement handle, or nothing if it couldn't be executed.

=item those, and stages at the end

returns what C<iterate> does: an iterator over the results, or, if the last stage is a sink, the sink's result.

=back

A hash reference or C<undef> straight after the statement is the
attributes to prepare it with. The statement can be a statement
handle, which is itself executed, or iterated over.

    use DBIx::Squirrel::Sugar database => {music => ['dbi:SQLite:dbname=music.db', '', '', {RaiseError => 1}]};

    say music('SELECT name FROM artist WHERE id = ?', 1)->fetchrow_arrayref->[0];    # Abba
    say ref music('SELECT name FROM artist', sub { $_->[0] });                        # DBIx::Squirrel::Iterator
    say join ' ', music(
        'SELECT name FROM artist ORDER BY id',
        sub { $_->[0] },
        keep_all,
    );
    # Abba Blur Cream


=head2 statement

    $function = statement($name, $database, $statement, @stages);
    $function = statement($name, $database, $statement, \%attr, @stages);

Defines a statement by that name, on the database of that name. The
attributes are those to prepare it with, and the stages are its own.
It gives the calling package a function of that name, and returns the
function. The database is found when the function runs, so it can be
defined after the statement.

A stage in a definition can be a pipeline's B<name>, as
Ekorn::Pipeline names them with C<named>: words joined by C<::>. A name
is looked up as the statement is defined, in the package defining it,
unless it's qualified, as C<My::Module::clean>, and stands in its place
among the stages. So it must be defined first, and one that isn't
croaks then: C<No pipeline named main::clean>. On C<use>, the definition
is made as the program compiles, so define the name in a C<BEGIN> block
before it.

=head2 The function a statement is given

    $sth     = artist(@bind_values);
    $it      = artist(@bind_values, @stages);
    @results = artist(@bind_values, @stages, $sink);

It executes the statement with the bind values, and returns the
statement handle, or nothing if it couldn't be executed. With stages,
its own or those given after the bind values, it returns an iterator
over the results, or, if the last stage is a sink, the sink's result,
as C<iterate> does. The results go through its own stages, then those
given. Stages given are for that call only. A string given is always a
bind value, never a pipeline's name.

    use Ekorn::Pipeline;

    BEGIN { Ekorn::Pipeline->named(shouted => sub {uc}) }

    use DBIx::Squirrel::Sugar statement => {
        artist_names => [music => 'SELECT name FROM artist ORDER BY id', sub { $_->[0] }],
        loud_names   => [music => 'SELECT name FROM artist ORDER BY id', sub { $_->[0] }, 'shouted'],
        artist       => [music => 'SELECT * FROM artist WHERE id = :id'],
    };

    say ref artist_names;                            # DBIx::Squirrel::Iterator
    say join ' ', artist_names keep_all;             # Abba Blur Cream
    say join ' ', artist_names sub {lc}, keep_all;   # abba blur cream
    say artist_names count_items;                    # 3
    say join ' ', loud_names keep_all;               # ABBA BLUR CREAM
    say artist(id => 3)->fetchrow_hashref->{name};   # Cream

A sink, imported, is a function of your package, so a statement can't
be given its name: C<Expected no function of the name in main already
(count_items)>. With Tooling's C<:all>, that's any name it exports.
Import fewer tags, or by name, or call one by its full name,
C<Ekorn::Pipeline::Sinks::count_items()>.

The statement is prepared once for each database handle, with
C<prepare_cached>. Its handle may be in use: by a statement handle not
read to the end, or by an iterator of an earlier call still reading. A
call then prepares one of its own. A statement taking a L<list|/"Lists">
is prepared for each call's values instead, and isn't cached.

=head1 13. Caching and connections

The user guide's L<chapter 13|DBIx::Squirrel::Manual::HowTo/"13. Caching and connections">.

=head2 prepare_cached

    $sth = $dbh->prepare_cached($statement);
    $sth = $dbh->prepare_cached($statement, \%attr);
    $sth = $dbh->prepare_cached($statement, \%attr, $if_active);

As C<prepare>, using the DBI's cache of statement handles. Its errors
name C<prepare_cached>, as the DBI's do. Like C<prepare>, it croaks
given a statement taking a L<list|/"Lists">.

Two statements can be rewritten the same: C<SELECT :a, :b> and
C<SELECT :b, :a> both become C<SELECT ?, ?>. Each still has a handle of
its own, as the statement as written is part of the cache's key.
DBIx::Squirrel's own attributes are part of the key too. So a
statement prepared with C<< {ekorn_slice => {}} >> and one prepared without
have different handles.

The DBI finishes a cached handle that's still active before handing it
out. If an iterator is part way through the handle, that would cut its
results short. So such a handle isn't handed out or finished. A new
handle is made instead, and cached in its place. The exception is
C<$if_active> of 2, which asks for the cached handle, unchanged.
Otherwise, C<$if_active> means what it does to the DBI. A cached handle
that's active, with no iterator, is finished, after a warning, unless
C<$if_active> says otherwise.

    my $sql   = 'SELECT name FROM artist ORDER BY id';
    my $first = $dbh->prepare_cached($sql)->iterate(sub { $_->[0] });
    $first->next;
    my $second = $dbh->prepare_cached($sql)->iterate(sub { $_->[0] });
    say $first->sth == $second->sth ? 'shared' : 'a handle each';    # a handle each
    say join ' ', $second->all;    # Abba Blur Cream
    say join ' ', $first->all;     # Blur Cream

=head2 connect_cached

C<connect_cached> is the DBI's own. It calls C<connect> when it needs a
new connection, so it croaks on failure too. DBIx::Squirrel's own
attributes are part of the cache's key. Two calls with the same
attributes have the same handle, and calls with different ones don't.

=head2 The Sugar's connections

A Sugar database is connected to when it's first used, not when it's
defined, with C<connect_cached>. So two databases defined with the same
arguments share a handle. The handle is kept, and each use has the
same one, without a ping to the database each time. It's pinged only
while its last call has failed, which leaves the error to be read.
It's made again if the connection has gone, or if the handle has been
disconnected. So the call after a connection drops fails, as it would
with plain DBI, and the call after that has a new connection.

=head1 14. Writing stages, and functions that take them

The user guide's L<chapter
14|DBIx::Squirrel::Manual::HowTo/"14. Functions that take stages, and stages for others">.

=head2 A function that takes stages

A function can take stages from its caller, at the end of its
arguments, and hand them to C<iterate> after its values. Its caller
then gets an iterator, or, with a sink last, the sink's result. To
find the stages at the end of a list of arguments, test each from the
end with Ekorn::Pipeline's C<is_stage>, which is true of code
references, pipelines and Ekorn's stage objects, and false of strings
and other values:

    use Ekorn::Pipeline qw(is_stage);

    sub albums_since ($year, @stages) {
        return $dbh->iterate('SELECT title FROM album WHERE year >= ? ORDER BY year', $year, @stages);
    }

    say albums_since(1990, count_items);    # 2
    say is_stage(sub {1}) ? 'a stage' : 'a value';    # a stage
    say is_stage('name') ? 'a stage' : 'a value';     # a value

=head2 Stages for others

A stage of your own is a code reference, or a pipeline of other
stages. Ekorn's reference, in L<Writing
stages|Ekorn::Pipeline::Manual::Reference/"Writing stages">,
and its user guide, in L<Building parts for
others|Ekorn::Pipeline::Manual::HowTo/"10. Building parts for others">,
say how to write one that works alongside the canned stages:

=over 4

=item *

a function that makes it, checking its options once;

=item *

state in a C<gather> block, so it starts afresh on each run;

=item *

a flush, for a stage that holds values, and an end, for one that
holds something to release;

=item *

C<Stop>, for one that knows no more are wanted;

=item *

a tap that returns the value it was given;

=item *

names, exports and tests.

=back

What follows is what's particular to stages for rows.

B<The shapes of a row.> A row can be an array, a hash (with the
C<ekorn_slice> attribute), or a row object (from C<results>). A stage
for others should say which it takes, or take all three, as C<pluck>
does. A stage that needs the statement's column names reads them from
the L<run's context|/"The run's context">.

B<Errors.> A function that makes a stage croaks when it's given the
wrong things, so the message names the line that called it. A module
of stages sets its C<@CARP_NOT> to DBIx::Squirrel's internal packages,
which take in the DBI's and Ekorn::Pipeline's. Then what it croaks
while a row goes through its stage is reported at the line that asked
for the result, not inside DBIx::Squirrel:

    package My::Stages {
        use DBIx::Squirrel::Errors qw(croakf);

        our @CARP_NOT = @DBIx::Squirrel::Errors::INTERNAL;

        sub prefixed ($prefix) {
            croakf 'Expected a prefix' unless defined $prefix && length $prefix;
            return sub ($value) {"$prefix$value"};
        }
    }

    say join ' ', $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        sub { $_->[0] },
        My::Stages::prefixed('#'),
    )->all;
    # #Abba #Blur #Cream

    eval { My::Stages::prefixed('') };
    print $@;    # Expected a prefix at ... line ...

C<croakf> croaks with a message made by C<sprintf>. Its format is a
literal, written in the code, with the values as its arguments. Never
make the format from data: it does whatever its C<%> directives say.

B<Where they go.> A stage goes where what it needs to know is. One
that needs a database, a statement, a row's column names, or the row a
result came from goes under C<DBIx::Squirrel::Stages::>. One that would
work on values from anywhere belongs under
C<Ekorn::Pipeline::Stages::>, where any function's stages can use it,
even if it was written for rows. Ekorn::Pipeline can't depend on
DBIx::Squirrel, so a stage that would C<use> DBIx::Squirrel goes under
C<DBIx::Squirrel::Stages::>. A stage added under
C<Ekorn::Pipeline::Stages::> reaches DBIx::Squirrel's users only once
DBIx::Squirrel adds it to the names its own modules of stages export.
The user guide's L<Decide where a stage
belongs|DBIx::Squirrel::Manual::HowTo/"Decide where a stage belongs"> says how to choose.

B<Testing.> A pipeline called with values tests a stage without a
database. Run it twice, to show it starts afresh. Then run it on rows
from an in-memory SQLite database, in each shape it takes.

B<Publishing.> Name a module of stages for its job, as
C<DBIx::Squirrel::Stages::CSV>, in a distribution named
C<DBIx-Squirrel-Stages-CSV>. Have it require the DBIx::Squirrel it was
tested with: v3.0.0 is the first with sinks, C<|> and the run's context
described in L<15. Protocols|/"15. Protocols">.

=head1 15. Protocols

What other code can rely on: the contracts between DBIx::Squirrel and
Ekorn::Pipeline, and between a statement's run and the stages reading
it. They're Ekorn::Pipeline's protocols, as DBIx::Squirrel keeps them;
Ekorn's reference describes the protocols themselves, in L<Delivering
parts for
Ekorn|Ekorn::Pipeline::Manual::Reference/"Delivering parts for Ekorn">.

=head2 The iterator as a source

A C<DBIx::Squirrel::Iterator>, and so a result set, is a source, as
Ekorn::Pipeline takes one: it offers C<EKORN_SOURCE>, the role method a
pipeline's C<iterator>, a chain made with C<|> and C<@{}> call. You don't
call it yourself. Each call starts a fresh run of the statement, from
its first row:

=over 4

=item *

the statement is executed again, finishing it first if it's active,
as C<reset> does, with the iterator's bind values;

=item *

the rows go through the iterator's own stages before they leave it,
so a pipeline reading it gets its results, not its rows;

=item *

the run's context is the statement's (see below);

=item *

the run is the iterator's: one it had going ends, and C<ended> says
how this one ended;

=item *

if another iterator over the same statement handle has results left,
it croaks, C<Expected the statement handle's other iterator to be
finished>, rather than take the handle from under it.

=back

A run reading the iterator reads on even if the iterator itself is let
go first, and finishes the statement when it ends.

    use Ekorn::Pipeline;

    my $it   = $dbh->iterate('SELECT name FROM artist ORDER BY id', sub { $_->[0] });
    my $next = Ekorn::Pipeline->new(sub {uc})->iterator($it);
    undef $it;
    my @names;
    while (my($name) = $next->()) { push @names, $name }
    say "@names";    # ABBA BLUR CREAM

=head2 The run's context

A run reading a statement, whether the iterator's own or a pipeline's
reading it, has the statement's context, which a stage asks for with
C<Ekorn::Pipeline::run_context()>. It's a hash reference:

=over 4

=item C<statement>

The statement handle, a C<DBIx::Squirrel::st>.

=item C<columns>

A reference to an array of the statement's column names, as C<fetchrow_hashref> keys them, following C<FetchHashKeyName>, read when the statement was executed.

=item C<row>

The row the statement gave last, as fetched, or as a row object for a result set: the row the value a stage is working on came from. C<undef> once the run has ended.

=back

A run whose context has a C<statement> that's a C<DBIx::Squirrel::st> is
reading a statement; any other run, such as a pipeline called with
values, has some other context, or none. C<pluck>, C<as_hash> and
C<result_original> read it, and so can a stage of yours. While a flush
gives its values, which come from every row, not one,
C<Ekorn::Pipeline::ending()> is true, and the row is no value's;
C<result_original> gives C<undef> then.

    my $columns = sub ($row) {
        my $context = Ekorn::Pipeline::run_context();
        return join ', ', map {"$_=$row->[$_ eq 'id' ? 0 : 1]"} @{ $context->{columns} };
    };
    say join '; ', $dbh->iterate('SELECT id, name FROM artist ORDER BY id', $columns)->all;    # id=1, name=Abba; id=2, name=Blur; id=3, name=Cream

The context is the run's: a pipeline called inside a stage has its
own, which has no row unless it too reads a statement.

=head2 What a call takes as stages

C<iterate>, C<results>, an iterator's C<reset>, the select methods,
C<pipe>, C<tap> and the Sugar's functions take as stages, at the end of
their arguments, whatever Ekorn::Pipeline's C<is_stage> is true of:
code references, pipelines, and Ekorn's stage objects, among them
stages made with C<gather>, Ekorn's words and the canned stages, and
its sinks. Anything else is a bind value, so an object of your own
given as a value stays one. A sink, if one is last, says what the call
gives (see L<8. Sinks|/"8. Sinks">). Only a Sugar statement's definition
takes pipelines' names, as strings.

=head2 What a gather's block returns

A C<gather> block, Ekorn's protocol for a part made for each run,
returns its step, flush and end, as a list or by name in a hash
reference (see L<gather|/"gather">). DBIx::Squirrel adds nothing to it;
Ekorn's reference has it in full, in
L<gather|Ekorn::Pipeline::Manual::Reference/"gather">.

=head1 16. Errors and diagnostics

The user guide's L<chapter 15|DBIx::Squirrel::Manual::HowTo/"15. When things go wrong">.

=head2 Errors

Errors are reported at the line of your code that called
DBIx::Squirrel, never at a line inside it or the DBI. That includes
the DBI's own errors under C<RaiseError>, such as
C<DBD::SQLite::db prepare failed: near "SELEC": syntax error>, which
keep the DBI's message.

DBIx::Squirrel croaks where the DBI would return C<undef> in C<connect>,
C<prepare> and C<prepare_cached>. The error then has the message the DBI
raises under C<RaiseError>, so it reads the same whatever C<RaiseError>
is set to.

Each error names the method you called, as plain DBI does: C<do> and
the select methods, not the C<prepare> or C<execute> they call;
C<selectall_array>'s errors name C<selectall_arrayref>, as the DBI's do.

An error from a C<HandleError> callback, or one that isn't a string, is
passed on unchanged. The DBI's warnings, under C<PrintError>, its
default, are reported the same way plain DBI reports them: at your
line, naming the method you called.

    eval { $dbh->prepare('SELEC name FROM artist') };
    print $@;    # DBD::SQLite::db prepare failed: near "SELEC": syntax error at ... line ...

=head2 Diagnostics

These are DBIx::Squirrel's own messages, and the messages of
Ekorn::Pipeline's that its users meet. Each is reported at the
caller's line. Those starting "Expected" say what was expected.

=head3 Connecting, preparing and binding

=over 4

=item C<Expected a statement>

The statement was blank, or a reference other than those C<prepare> takes.

=item C<Expected one placeholder style, not several (%s)>

The statement mixed styles, such as C<?> and C<:name>. Each is listed as an example.

=item C<Expected placeholders numbered from 1 (%s)>

A numbered placeholder such as C<$0>.

=item C<Expected ekorn_slice to be a reference to an ARRAY or HASH>

C<ekorn_slice> was something else.

=item C<Expected a reference to a HASH or ARRAY>

The first argument after the statement in C<do>, C<iterate>, C<results> or a select method was a reference, but not to a hash or an array.

=item C<Expected %d bind values, not %d>

A statement with numbered placeholders was given more or fewer values than its highest number.

=item C<Expected names and values in pairs>

A statement with named placeholders was given an odd number of values.

=item C<Expected a placeholder of the statement (%s)>

A value was given for a placeholder the statement doesn't have.

=item C<Expected a value for each placeholder (none for %s)>

A statement with named placeholders wasn't given a value for each name, or a statement with numbered or named placeholders was executed without values when some had none bound.

=item C<Expected bind values with a statement taking a list (%s)>

C<prepare> or C<prepare_cached> was given a statement taking a L<list|/"Lists">. Each list placeholder is named, and a C<?> is named by its position: C<...? at 2>.

=item C<Expected a placeholder to take a list everywhere or nowhere (%s)>

A placeholder was used with C<...> in one place and without it in another.

=item C<Expected no list placeholder with pg_placeholder_dollaronly (%s)>

A C<$1> placeholder took a list under DBD::Pg's C<pg_placeholder_dollaronly>.

=item C<Expected a reference to an ARRAY for a list (%s)>

A list placeholder was given a plain value, C<undef>, or a reference to something other than an array.

=item C<Expected at least one value in a list (%s)>

A list placeholder was given an empty list.

=item C<Expected plain values in a list (%s)>

A list held a reference, as C<[[1, 2]]> does to a statement whose one value is a list.

=item C<Expected %d values in a list, as prepared, not %d (%s)>

The handle of a statement taking a list was executed or bound with a list of another length.

=back

=head3 Iterators and result sets

=over 4

=item C<Expected a statement handle>

C<< DBIx::Squirrel::Iterator->new >> wasn't given a C<DBIx::Squirrel::st>.

=item C<Expected only one item, but there were more>

A warning: C<single>, C<keep_single> or C<take_single> found a second result, and gave the first.

=item C<Expected the statement handle's other iterator to be finished>

Another iterator over the same statement handle has results left.

=item C<Expected ekorn_result_class to be a subclass of DBIx::Squirrel::Result (%s)>

C<ekorn_result_class> named a class that isn't one.

=item C<Expected a column of the row (%s)>

C<get_column> or C<pluck> was given a name or position the row doesn't have.

=item C<Expected use Ekorn::Pipeline::Operators in scope, for %s>

C<|> or C<@{}> was used on an iterator where the operators aren't in force.

=back

=head3 Pipelines

=over 4

=item C<Expected stage #%d to be a code reference or a pipeline>

Something passed as a stage to a pipeline, C<pipe> or C<tap> wasn't one. No stage runs.

=item C<Expected a code reference>

The block given to C<gather>, C<take_while>, C<drop_while>, C<take_if>, C<drop_if>, C<collect> or C<peek>, or the source given to a pipeline's C<iterator>, wasn't a code reference.

=item C<Expected stage #%s, made with gather, to return a code reference or a pipeline, and optionally a flush and an end>

The block given to C<gather> for that stage returned something else.

=item C<Pipeline stage #%s failed at %s line %d:>

A stage, or its flush, died. The message it died with follows, indented. See L<When a stage dies|/"When a stage dies">.

=item C<Pipeline end of stage #%s failed at %s line %d:>

A stage's end died, in a run that hadn't died already.

=item C<Stop used outside a pipeline>

C<Stop> was called where no pipeline was running to catch it.

=item C<No pipeline named %s>

A name, in a Sugar statement's definition or given to C<pipeline>, has no pipeline.

=back

=head3 Canned stages and sinks

=over 4

=item C<Expected a count of 0 or more>

C<take>, C<drop> or C<keep> was given something other than a whole number.

=item C<Expected a batch size of 1 or more>

C<batch> was given something other than a whole number above 0.

=item C<Expected a column, by name or position>

C<pluck> was given no column, or an empty name.

=item C<Expected an iterator, for the column names>

C<as_hash>, or C<pluck> with a name for an array row or a position for a hash row, ran where no statement was being read, such as in a pipeline called with values.

=item C<Expected a row: an array, a hash or a row object>

C<pluck> or C<as_hash> was given a value that isn't a row.

=item C<Expected a reference to a scalar>

C<count_into> was given something else.

=item C<Expected an open filehandle>

C<dump_to> or C<to_fh> was given something else.

=back

=head3 Sugar

=over 4

=item C<Expected database or statement, not %s>

C<use DBIx::Squirrel::Sugar> was given something else.

=item C<Expected the arguments to connect to %s in an ARRAY>

A database's definition, given to C<use>, wasn't an array reference.

=item C<Expected the statement %s in an ARRAY>

A statement's definition, given to C<use>, wasn't an array reference.

=item C<Expected a name for a database (%s)>

The name can't be a function's.

=item C<Expected a name for a statement (%s)>

The name can't be a function's.

=item C<Expected a database defined once (%s)>

The name was given to another database already.

=item C<Expected a database defined as %s>

C<database> was given a name no database has.

=item C<Expected a database and a statement for %s>

A statement's definition didn't name its database, or have its SQL.

=item C<Expected only code references, pipelines or their names after the statement for %s>

A statement's definition had something other than stages, which are code references, pipelines or pipelines' names, after the statement and its attributes.

=item C<Expected no function of the name in %s already (%s)>

The package has a function of that name already, such as a sink it imported.

=back

=head1 Making each kind of part

This section is for developers making parts for DBIx::Squirrel's
users: what a statement's run gives each piece of a part, and a worked
example of each kind DBIx::Squirrel adds to, made with a word and as a
class of your own. The protocol itself, what each piece is called
with, what it returns, and the rules every part keeps, is
Ekorn::Pipeline's, and its reference has it in full, in L<Making each
kind of part|Ekorn::Pipeline::Manual::Reference/"Making each kind of part">.
Each example runs against the examples' database, and its comments say
what it prints.

=head2 What a statement's run gives each piece

A part reading a statement, through C<iterate>, C<results>, a Sugar
function, C<|>, or a pipeline of yours reading an iterator, finds the
statement in the L<run's context|/"The run's context">. What each piece
finds there, and what L<Context|/"Context">'s functions give it:

=over 4

=item B<set-up>

**C<Ekorn::Pipeline::run_context()>:** nothing: the run hasn't read the statement yet

**C<result_original>:** C<undef>

**C<result_number>, in an iterator's own run:** C<undef>

=item a stage's B<step>

**C<Ekorn::Pipeline::run_context()>:** C<statement>, C<columns>, and the C<row> this value came from

**C<result_original>:** the row

**C<result_number>, in an iterator's own run:** the number of the result being made

=item a stage's B<flush>

**C<Ekorn::Pipeline::run_context()>:** C<statement> and C<columns>; C<ending()> is true, and the row is no value's

**C<result_original>:** C<undef>

**C<result_number>, in an iterator's own run:** the number of the first value it gives

=item a sink's B<step>

**C<Ekorn::Pipeline::run_context()>:** C<statement>, C<columns> and C<row>, as for a stage

**C<result_original>:** the row

**C<result_number>, in an iterator's own run:** not the value's number, which has been counted: a sink counts for itself

=item a sink's B<flush>

**C<Ekorn::Pipeline::run_context()>:** as for a stage's flush

**C<result_original>:** C<undef>

**C<result_number>, in an iterator's own run:** not used

=item an B<end>

**C<Ekorn::Pipeline::run_context()>:** C<statement> and C<columns>; the C<row> is C<undef>

**C<result_original>:** C<undef>

**C<result_number>, in an iterator's own run:** not used

=back

So a stage that needs the statement's columns reads them in its step,
the first time it's called in the run, and keeps them in a variable of
the set-up, as C<pluck> and C<as_hash> do. It can't read them in the
set-up, which runs before the statement does.

=head2 A stage for rows, with the word C<gather>

A stage that gives each row, an array, as its columns and values, and
says how many rows there were once they run out. It croaks if what it
reads isn't a statement, in a module of stages, as L<Stages for
others|/"Stages for others"> says, so the message names the caller's
line:

    package My::Stages {
        use DBIx::Squirrel::Errors qw(croakf);
        use DBIx::Squirrel::Tooling qw(gather);

        our @CARP_NOT = @DBIx::Squirrel::Errors::INTERNAL;

        sub labelled () {
            return gather {
                my($columns, $n) = (undef, 0);    # this run's
                return {
                    step => sub ($row) {
                        $columns //= do {
                            my $context = Ekorn::Pipeline::run_context();
                            croakf 'Expected a statement to read, for its columns'
                                unless ref $context eq 'HASH'
                                && $context->{statement} isa 'DBIx::Squirrel::st';
                            $context->{columns};
                        };
                        $n++;
                        return join ', ', map {"$columns->[$_]=$row->[$_]"} 0 .. $#$columns;
                    },
                    flush => sub () {"($n rows)"},
                };
            };
        }
    }

    say for $dbh->iterate(
        'SELECT id, name FROM artist ORDER BY id',
        My::Stages::labelled,
    )->all;
    # id=1, name=Abba
    # id=2, name=Blur
    # id=3, name=Cream
    # (3 rows)

    say for $dbh->iterate(
        'SELECT id, name FROM artist ORDER BY id',
        My::Stages::labelled,
        take(1),
    )->all;
    # id=1, name=Abba

    eval { Ekorn::Pipeline->new(My::Stages::labelled)->([1, 'Abba']) };
    print $@;
    # Pipeline stage #1 failed at ... line ...:
    #     Expected a statement to read, for its columns at ... line ...

In the second run, C<take(1)>, after it, stopped the run while rows
were still to come, so its flush wasn't called, as Ekorn's rules say.
Called with values, the pipeline reads no statement, so the stage
croaks.

=head2 The same stage, as a class

A class of your own can be the same stage, by offering C<EKORN_STAGE>,
called at the start of each run with the object, and returning the
pieces, as the set-up did. The object keeps its settings, and each run
its own columns:

    package My::Labelled {
        sub new ($class, %options) { bless {between => $options{between} // ', '}, $class }

        sub EKORN_STAGE ($self) {
            my $columns;    # this run's
            return {
                step => sub ($row) {
                    $columns //= Ekorn::Pipeline::run_context()->{columns};
                    return join $self->{between}, map {"$columns->[$_]=$row->[$_]"} 0 .. $#$columns;
                },
            };
        }
    }

    say for $dbh->iterate(
        'SELECT id, name FROM artist ORDER BY id',
        My::Labelled->new(between => ' '),
    )->all;
    # id=1 name=Abba
    # id=2 name=Blur
    # id=3 name=Cream

=head2 A sink into a table, with the word C<sink_one>

A sink that inserts each value into a table, and gives how many it
inserted. Its set-up begins a transaction, and its end commits it only
if the run ended C<done>, so a run that dies, or is stopped, leaves the
table as it was:

    sub into ($dbh, $table) {
        return sink_one {
            my $n = 0;
            $dbh->begin_work;
            my $sth = $dbh->prepare("INSERT INTO $table (name) VALUES (?)");
            return {
                step  => sub ($name) { $sth->execute($name); $n++ },
                flush => sub ()      {$n},
                end   => sub ($how)  { $how eq 'done' ? $dbh->commit : $dbh->rollback },
            };
        };
    }

    $dbh->do('CREATE TEMP TABLE copy (name TEXT)');

    say $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        pluck('name'),
        into($dbh, 'copy'),
    );
    # 3

    eval {
        $dbh->iterate(
            'SELECT name FROM artist ORDER BY id',
            pluck('name'),
            sub { die "no Cream\n" if $_ eq 'Cream'; $_ },
            into($dbh, 'copy'),
        );
    };
    print $@;
    # Pipeline stage #2 failed at ... line ...:
    #     no Cream

    say $dbh->selectrow_array('SELECT COUNT(*) FROM copy');    # 3

The second run inserted Abba and Blur, then died at Cream, so the sink's
end was told C<died>, and rolled them back: the table has the first
run's three rows.

=head2 The same sink, as a class

A class offers C<EKORN_SINK_ONE> for a sink of one result, or
C<EKORN_SINK_MANY> for a sink of many, returning the same pieces:

    package My::Into {
        sub new ($class, $dbh, $table) { bless {dbh => $dbh, table => $table}, $class }

        sub EKORN_SINK_ONE ($self) {
            my($dbh, $n) = ($self->{dbh}, 0);
            $dbh->begin_work;
            my $sth = $dbh->prepare("INSERT INTO $self->{table} (name) VALUES (?)");
            return {
                step  => sub ($name) { $sth->execute($name); $n++ },
                flush => sub ()      {$n},
                end   => sub ($how)  { $how eq 'done' ? $dbh->commit : $dbh->rollback },
            };
        }
    }

    say $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        pluck('name'),
        take(2),
        My::Into->new($dbh, 'copy'),
    );
    # 2

    say $dbh->selectrow_array('SELECT COUNT(*) FROM copy');    # 5
    $dbh->do('DROP TABLE copy');

C<take(2)> stopped the run, but before the sink, so the sink got every
value it was going to get: its end was told C<done>, and it committed.

=head2 Row classes and functions that take stages

A row class of your own, for C<results>, is a subclass of
DBIx::Squirrel::Result with methods of your own: see L<Methods of your
own|/"Methods of your own">. A function that takes stages from its
caller hands them to C<iterate>: see L<A function that takes
stages|/"A function that takes stages">. Neither has pieces of its own.

=head1 Differences from plain DBI

Where DBIx::Squirrel and plain DBI do the same thing, they give the
same result. These are the places they differ.

=over 4

=item Placeholders

B<Plain DBI:> C<?>, and whatever the driver adds.

B<DBIx::Squirrel:> C<?>, C<?1>, C<:1>, C<$1>, C<:name> and C<$name>, rewritten as C<?> for the DBI.

=item Numbered and named placeholders

B<Plain DBI:> Bound by position.

B<DBIx::Squirrel:> Bound once, by number or name, wherever they appear.

=item Lists, as for C<IN>

B<Plain DBI:> A C<?> for each value, written out.

B<DBIx::Squirrel:> C<...?>, C<...$1> or C<...:name>, written as a C<?> for each value of the list given.

=item C<connect> failing

B<Plain DBI:> Returns C<undef>, unless C<RaiseError>.

B<DBIx::Squirrel:> Always croaks, with the DBI's C<RaiseError> message.

=item C<prepare> failing

B<Plain DBI:> Returns C<undef>, unless C<RaiseError>.

B<DBIx::Squirrel:> Always croaks, with the DBI's C<RaiseError> message.

=item Attributes in C<do> and the select methods

B<Plain DBI:> Required, or C<undef>, before the bind values.

B<DBIx::Squirrel:> May be left out.

=item A lone array reference of bind values

B<Plain DBI:> A value.

B<DBIx::Squirrel:> The values in it, except for a statement taking one value that's a list, or with DBD::Pg.

=item Where errors and warnings are reported

B<Plain DBI:> The line inside the module that called the DBI.

B<DBIx::Squirrel:> The line of your code that called DBIx::Squirrel.

=item Statements

B<Plain DBI:> A string.

B<DBIx::Squirrel:> A string, lines in an array reference, a code reference returning either, or a statement handle.

=item Executing an active statement

B<Plain DBI:> Left to the driver.

B<DBIx::Squirrel:> The same, or finished first with C<ekorn_finish_active>.

=item Executing with placeholders unbound

B<Plain DBI:> Left to the driver, which most read as C<NULL>.

B<DBIx::Squirrel:> Croaks, for numbered and named placeholders: C<Expected a value for each placeholder (none for id)>.

=item Stages after the select methods' values

B<Plain DBI:> None.

B<DBIx::Squirrel:> What the DBI gives is pushed through them.

=item Iterators, result sets, pipelines

B<Plain DBI:> None.

B<DBIx::Squirrel:> C<iterate>, C<results>, sinks, C<|> and C<@{}>, C<pipe>, C<tap> and the Sugar.

=back

=head1 Upgrading from 2.x

Version 3 builds on Ekorn::Pipeline v0.3.0, and makes one rule of what
a call gives: a statement is a source; DBIx::Squirrel's calls give an
iterator, and only a sink given last turns it into a result. These are
the changes code written for 2.x meets, and how to move:

=over 4

=item A Sugar statement given stages, read as a list: C<my @names = artist_names sub {...}>

B<What happens now:> gives an iterator, not every result

B<How to move:> give a sink last: C<artist_names sub {...}, keep_all>

=item A Sugar statement given stages in scalar context, for a count

B<What happens now:> gives an iterator

B<How to move:> give C<count_items> last

=item C<< $it->count >>

B<What happens now:> fails: the method is gone

B<How to move:> give C<count_items> last, or count as you go with C<count_into(\$n)>

=item C<< my $n = $it->all >>, for a count

B<What happens now:> an array reference

B<How to move:> C<count_items> given last

=item C<< $it->single >>, after C<next>

B<What happens now:> the next result, not a fresh run's only one

B<How to move:> C<< $it->reset->single >>

=item C<< $it->single >>, at a second result

B<What happens now:> a warning, and the first, not a croak

B<How to move:> check for the warning, or keep the croak with a stage of your own

=item C<< DBIx::Squirrel::Pipeline->new(...) >>

B<What happens now:> fails: the module is gone

B<How to move:> C<< Ekorn::Pipeline->new(...) >>, or C<pipeline(...)> from Ekorn::Pipeline::Factories

=item C<$x isa 'DBIx::Squirrel::Pipeline'>

B<What happens now:> false

B<How to move:> C<$x isa 'Ekorn::Pipeline'>

=item C<< DBIx::Squirrel::Stop->throw >>, or a subclass of DBIx::Squirrel::Stop

B<What happens now:> fails: it's no longer a class

B<How to move:> C<< Ekorn::Pipeline::Stop->throw >>, and subclass C<Ekorn::Pipeline::Stop>

=item C<ref $stage eq 'CODE'>, or C<is_coderef($stage)>, for a stage made by C<take>, C<gather> and the like

B<What happens now:> false: they're objects now, called as code references

B<How to move:> C<is_stage($stage)>, from Ekorn::Pipeline

=item A C<gather> block's second part, "the end function"

B<What happens now:> the same, now called the flush

B<How to move:> nothing; an end, told how the run ended, can follow it

=item C<result_number> or C<iterator> in a pipeline of your own reading an iterator

B<What happens now:> C<undef>

B<How to move:> count in a stage of your own

=item C<< my($first) = $sth->iterate->next >>, then using the handle

B<What happens now:> the handle is finished once the iterator goes

B<How to move:> keep the iterator while the handle is in use

=back

Everything else works as it did: C<iterate>, C<results>, and the select
methods and Sugar without stages or a sink last, C<pluck>, C<as_hash>,
C<take>, C<Stop>, and C<gather>. New: C<first>, C<ended>, sinks given last,
C<|> and C<@{}>, stages for the select methods, named pipelines in the
Sugar's definitions, and the run's context as a documented protocol.

=head1 Upgrading from 1.x

DBIx::Squirrel 2 was a rewrite, not an update, and version 3 builds on
it. Code written for 1.x needs changes before it runs. The ideas carry
over, so most changes are a rename or a simpler call. But some methods
keep their names and change what they do. They're marked B<in bold>
below.

To stay on 1.x, which supports Perl 5.10.1 and later, install the last
version by its number:

    cpanm DBIx::Squirrel@1.6.5

=head2 Requirements and loading

=over 4

=item Perl 5.10.1 or later.

Perl 5.36 or later.

=item Hard dependencies on Compress::Bzip2, Crypt::CBC, Dotenv, JSON::Syck, YAML::Syck and others.

DBI, Ekorn::Pipeline, Ref::Util, namespace::clean, and a few core modules.

=item Loading it read a C<.env> file in the current directory, through Dotenv.

Nothing is read. Load your environment yourself.

=back

=head2 Importing and the entity helpers

=over 4

=item C<< use DBIx::Squirrel database_entities => [qw(db artists)]; >>

C<< use DBIx::Squirrel::Sugar database => {...}, statement => {...}; >>

=item A helper was associated at run time: C<< db(DBIx::Squirrel->connect(...)) >>.

A database is defined by the arguments to connect with, and connected when first used: C<< database => {db => [$dsn, $user, $pass]} >>.

=item A helper could hold a database, a statement or an iterator.

A function holds a database, or a statement on a database by name, with stages of its own.

=item A helper for a result set returned the iterator, so C<< artist('Aerosmith')->single->ArtistId >>.

A statement's function returns the statement handle, or, with stages, an iterator, or a sink's result: C<< artist('Aerosmith', sub ($row) { $row->[0] }, keep_single) >>.

=back

    # 1.x
    use DBIx::Squirrel database_entities => [qw(db artist)];
    db(DBIx::Squirrel->connect($dsn, $user, $pass));
    artist(db->results('SELECT * FROM artists WHERE Name = ? LIMIT 1'));
    say artist('Aerosmith')->single->ArtistId;

    # Now
    use DBIx::Squirrel::Sugar
        database  => {db => [$ENV{DSN}, $ENV{USER}, $ENV{PASS}]},
        statement => {artist_id => [db => 'SELECT ArtistId FROM artists WHERE Name = ?', sub ($row) { $row->[0] }]};
    use Ekorn::Pipeline::Sinks qw(keep_single);
    my $id = artist_id('Aerosmith', keep_single);

=head2 Placeholders and binding

=over 4

=item C<?>, C<?1>, C<:1>, C<$1> and C<:name>.

The same, and C<$name>.

=item Placeholders were found anywhere in the statement: in quoted strings, and in casts, so C<x::int> broke.

Not in quoted strings, comments, casts or PostgreSQL's dollar-quoted bodies, read by the database's rules. See L<What isn't a placeholder|/"What isn't a placeholder">.

=item Styles could be mixed.

One style to a statement. A mix croaks.

=item C<--> comments were removed before the statement reached the database.

Comments are passed on to the database.

=back

Binding by name, as pairs or in a hash reference, with or without the
sigil, works as it did.

=head2 do

=over 4

=item **In list context, C<do> returned the row count and the statement handle.**

C<do> returns what the DBI's returns, in any context. Use C<prepare> and C<execute> for the handle.

=back

=head2 Iterator and result set methods

=over 4

=item C<it> and C<iterator>, aliases of C<iterate>.

C<iterate> only.

=item C<rs> and C<resultset>, aliases of C<results>.

C<results> only.

=item C<< $dbh->iterate($sql, [@bind_values, @transforms]) >>: values and stages in one array reference.

Stages are at the end of the arguments: C<< $dbh->iterate($sql, @bind_values, @stages) >>.

=item **C<next> put the result in C<$_>**, as in C<< while ($it->next) { say $_->Name } >>.

Nothing is put in C<$_>: C<< while (my($row) = $it->next) { say $row->name } >>.

=item C<all> in scalar context returned a reference to the results.

The same.

=item **C<count> fetched the rest of the results and returned how many there were in all.**

Gone: give C<count_items> last, as C<< $dbh->iterate($sql, count_items) >>.

=item C<count_fetched>.

Gone: C<count_into(\$n)> as a stage, or C<result_number> in one.

=item C<single> and C<one> returned the first result, with a warning if there were more.

C<single> the same; C<one> is gone.

=item C<first>.

The same.

=item C<last> and C<last_fetched>.

Gone: C<keep_last> given last, or C<take_last> as a stage.

=item C<remaining>.

C<all>, which returns the results not yet handed out.

=item C<start> and C<iterate> on an iterator, to execute it with new bind values.

C<reset(@bind_values, @stages)>.

=item C<reset($slice, $cache_size)>, to change the slice or the cache size.

C<reset> takes bind values and stages. The slice is the C<ekorn_slice> attribute. Rows are fetched 2 at first, up to 64 at a time.

=item C<slice>, C<cache_size> and their package-wide defaults, C<$DBIx::Squirrel::it::DEFAULT_SLICE> among them.

The C<ekorn_slice> attribute, on C<connect> or C<prepare>.

=item C<is_active>, C<not_active> and C<rows>.

Gone: C<< $it->sth->{Active} >> and C<< $it->sth->rows >>.

=back

=head2 Rows as objects

=over 4

=item B<A column's method matched its name in any case:> C<< $row->ArtistId >> or C<< $row->artistid >>.

Methods are named in lower case only: C<< $row->artistid >>.

=item Methods were made the first time each was called.

A class with a method for each column is made for each list of columns. See L<Row objects|/"Row objects">.

=item A column whose name can't be a method's, such as C<COUNT(*)>, was reached by its position.

By its position still, as rows are arrays, or with C<get_column>, or given a name with C<AS>.

=back

=head2 Transformations, now stages

The stages work as transformations did. Each gets a value as its
argument and in C<$_>, and returns nothing to drop it, one value, or
several. These have changed:

=over 4

=item C<use DBIx::Squirrel::it qw(...)>, for what a stage can ask.

C<use DBIx::Squirrel::Context qw(...)>.

=item C<iterator>, C<result_number> and C<result_original>.

The same, from DBIx::Squirrel::Context.

=item C<database> and C<statement>.

C<< iterator->sth->{Database} >> and C<< iterator->sth >>, or the L<run's context|/"The run's context">.

=item C<result> and C<result_current>.

The stage's argument.

=item C<result_first>, C<result_prev>, C<result_previous> and C<result_offset>.

Gone. A stage that needs them keeps them itself, in a L<C<gather>|/"gather"> block.

=item C<DBIx::Squirrel::Transform::Data::Dumper>'s C<as_perl>, and C<DBIx::Squirrel::Transform::IO>'s C<stdout> and C<stderr>.

C<dump_to> and C<peek>, from DBIx::Squirrel::Stages::Taps. See L<Canned stages|/"Canned stages">.

=item No way to end a transformation early.

C<Stop>, from DBIx::Squirrel::Stop. See L<Stop|/"Stop">.

=back

=head2 Gone, out of scope

These have no place now. Any that come back will come back as
distributions of their own.

=over 4

=item C<DBIx::Squirrel::Crypt::Fernet>, and C<decrypt> from DBIx::Squirrel::util.

A Fernet module from CPAN.

=item C<DBIx::Squirrel::Transform::JSON::Syck> and C<DBIx::Squirrel::Transform::YAML::Syck>.

For JSON, C<from_json> and C<to_json>, from Ekorn::Pipeline::JSON, by Tooling's L<C<:json>|/"Importing: DBIx::Squirrel::Tooling">. For YAML, a stage of your own calling a YAML module: see L<Stages for others|/"Stages for others">.

=item C<get_file_contents>, C<slurp>, C<uncompress>, C<unmarshal> and C<utf8decode>, from DBIx::Squirrel::util.

Path::Tiny, IO::Uncompress::Bunzip2, a JSON module, and Encode.

=item C<load_tuples>, on a database handle.

C<prepare> and C<execute>, in a loop.

=item C<statement_digest>, C<statement_normalise>, C<statement_study> and C<statement_trim>, on a statement handle.

C<study_sql> and C<trim_sql>, from DBIx::Squirrel::Placeholders.

=back
