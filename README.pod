=head1 DBIx-Squirrel

DBI, minus the boilerplate, plus a pipeline.

With DBIx::Squirrel, you still write SQL, as you do with the DBI. It
takes away the friction around it: placeholders in whatever style you
like, iterators over results, and a pipeline of stages written beside
the query. It never hides the SQL, and it isn't an ORM.

    my @names = $dbh->iterate(
        'SELECT name FROM track WHERE plays > :plays ORDER BY plays DESC',
        plays => 6000,
        sub { $_->[0] },    # each row's name
        sub { uc },         # in capitals
    )->all;

It's a subclass of the DBI, so everything the DBI does still works.
Where the two do the same thing, they give the same result.

=head2 Why use it

The DBI is the right foundation, and it's low-level on purpose. Most
code written around it does the same few chores, by hand, each time.
DBIx::Squirrel does them for you.

=over

=item * B<Placeholders you can read.>

With C<?>, values go in the order the marks appear. A value used twice
is passed twice, and changing the SQL can mean changing the code that
calls it. Named placeholders bind by name, with each value given once.
They work on any driver, whatever placeholders it supports itself, so
SQL written with PostgreSQL's C<$1> runs unchanged on SQLite. Values
that don't match the placeholders croak, rather than being bound in
the wrong place.

=item * B<Rows that come out ready to use.>

There's no fetch loop to write, and no array to push onto. The stages
that map, filter and expand the rows sit beside the query. You can
read what a result holds next to the SQL that makes it. Rows are
fetched in batches, so you can work through a large result a row at a
time without holding all of it in memory. Ready-made stages do the
common jobs, such as taking the first few rows, picking out a column,
or handing rows out in batches.

=item * B<Queries with names.>

A statement and its stages can become a function with a name of its
own. The SQL is written in one place, and the code that uses it reads
as plainly as C<titles_by 2>.

=item * B<Nothing to unlearn, and nothing to undo.>

Your handles, attributes, drivers and existing code all still work,
because it's still the DBI. Use as much as helps, and stop there. It
isn't an ORM. You write the SQL, so everything your database can do is
still there, and it never runs a query you didn't write.

=back

=head2 One step at a time

You can take it up a step at a time, and stop at any step. Each works
on its own, and code written for the DBI keeps working at every one.

=head3 1. Connect with it.

    use DBIx::Squirrel;

    my $dbh = DBIx::Squirrel->connect('dbi:SQLite:dbname=music.db', '', '');

Your DBI code runs as it did. C<connect> and C<prepare> croak if they
fail, so there's no C<or die> to write.

=head3 2. Write placeholders in the style you like.

    my $sth = $dbh->prepare('SELECT title FROM album WHERE artist_id = :artist AND year > :year');
    $sth->execute(artist => 2, year => 1994);

    my $album = $dbh->selectrow_hashref('SELECT * FROM album WHERE id = $1', 2);

C<?>, C<?1>, C<:1>, C<$1>, C<:name> and C<$name> are each rewritten as
C<?> for the DBI. A numbered or named placeholder takes one value,
wherever it appears. C<do> and the select methods need no C<undef>
before the values.

    my $of_years = $dbh->selectall_arrayref('SELECT * FROM album WHERE year IN (...:years)',
        years => [1967, 1994]);

A placeholder with C<...> before it takes a list. It's written as a
C<?> for each value in the array reference given.

=head3 3. Iterate over the results.

    my $albums = $dbh->iterate('SELECT title, year FROM album ORDER BY year');
    while (my($row) = $albums->next) {
        say "$row->[0] ($row->[1])";
    }

Rows are fetched in batches, and the statement is finished when they
run out. C<all> takes the rest at once, nearly as quickly as plain
DBI. C<first> takes the next one, and C<single> the only one, warning
if there's another.

=head3 4. Add stages.

    my @hits = $dbh->iterate(
        'SELECT name, plays FROM track ORDER BY plays DESC',
        sub { $_->[1] >= 5000 ? $_ : () },    # leave out the rest
        sub { "$_->[0] ($_->[1])" },          # make each a string
    )->all;

Each row goes through the stages, given as C<$_>. A stage returns
nothing to drop the row, one value in its place, or several. It can
also stop the iteration early. A stage made with C<gather> can hold
rows, and give them out at the end, in batches or as one value.
C<pipe> runs anything else through stages the same way.

Ready-made stages come with it, for jobs that come up again and again.
They're in four modules: C<take> and C<drop> in
L<DBIx::Squirrel::Stages::Flow>, with C<take_if>, C<drop_if>,
C<take_while> and more on request, C<pluck> and C<as_hash> in
L<DBIx::Squirrel::Stages::Rows>, C<batch> and C<collect> in
L<DBIx::Squirrel::Stages::Batch>, and C<peek> and C<count_into> in
L<DBIx::Squirrel::Stages::Taps>.

A sink, given last, says what the call gives in place of an iterator:
C<keep_all> every result, C<count_items> how many, C<keep_first> the
first, and others. They're in L<Ekorn::Pipeline::Sinks>.
L<DBIx::Squirrel::Tooling> exports every stage, sink and word from one
module, by tags, as C<:stages> and C<:sinks>, or C<:all>:

    use DBIx::Squirrel::Tooling qw(:all);

    my @top_ten = $dbh->iterate(
        'SELECT name, plays FROM track ORDER BY plays DESC',
        take_if { $_->[1] >= 5000 },    # leave out the rest
        pluck('name'), take(10), keep_all,
    );

    my $hits = $dbh->iterate('SELECT * FROM track WHERE plays > ?', 6000, count_items);

Where L<Ekorn::Pipeline::Operators> is in scope, C<|> chains them too,
as in C<$it | count_items>. The reference says how to write your own
stages to work alongside them.

The pipeline is
L<Ekorn::Pipeline|https://github.com/nukopian/Ekorn-Pipeline>. It
began here, and is now a distribution of its own, so that any function
can take stages from its caller. DBIx::Squirrel uses it as it is, and
keeps its own names for its modules of functions, such as
C<DBIx::Squirrel::Stop>. The stages that need a database, such as
C<pluck>, are DBIx::Squirrel's own.

=head3 5. Have rows as objects.

    my $album = $dbh->results('SELECT * FROM album WHERE id = :id', id => 2)->single;
    say $album->title, ' (', $album->year, ')';

Each row has a method for each column, and stages can work on the
objects.

=head3 6. Give your databases and statements names.

    use DBIx::Squirrel::Tooling qw(keep_all);
    use DBIx::Squirrel::Sugar
        database  => {music => ['dbi:SQLite:dbname=music.db', '', '']},
        statement => {
            titles_by => [music => 'SELECT title FROM album WHERE artist_id = ?', sub { $_->[0] }],
        };

    my @titles = titles_by 2, keep_all;

L<DBIx::Squirrel::Sugar> makes each a function with its own name. A
statement's stages are declared beside its SQL. Called, it gives an
iterator over the results, or, with a sink last, the sink's result.

=head2 Installing

    cpanm DBIx::Squirrel

It needs Perl 5.36 or later.

=head2 Upgrading

This is version 3. It builds on Ekorn::Pipeline, and makes one rule of
what a call with stages gives: an iterator, unless a sink given last
says otherwise. Most code written for 2.x runs as it did, and
L<Upgrading from 2.x|DBIx::Squirrel::Manual::Reference/"Upgrading from 2.x">,
in the reference, lists what changes.

Version 2 was a rewrite. Code written for 1.x needs changes to run,
and
L<Upgrading from 1.x|DBIx::Squirrel::Manual::Reference/"Upgrading from 1.x">
lists them. To stay on 1.x, which also runs on older Perls, install
its last version:

    cpanm DBIx::Squirrel@1.6.5

Its code is in the archived
L<DBIx-Squirrel-1|https://github.com/nukopian/DBIx-Squirrel-1>
repository.

The repository was called DBIx-Squirrel-2 while version 2 was in
development. It took the original name, DBIx-Squirrel, before its
first release.
