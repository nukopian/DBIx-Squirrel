# 2026-0061. is_stage, from DBIx::Squirrel::Tooling

**Status:** open

**Decisions:** D1 settled: DBIx::Squirrel::Tooling, in `:core`; Part 1
keeps its function with a fixed number of values.

**Origin:** roadmap, added 2026-11-26, from 2026-0057's D4

## Background

A function taking any number of values, then stages, finds where the
stages start with Ekorn::Pipeline's `is_stage`, which is true of code
references, pipelines and Ekorn's stage objects. DBIx::Squirrel uses
it itself, in `db.pm`, `Sugar.pm` and `Util.pm`, but exports it from
none of its modules, so Part 1 of the documents shows only a function
with a fixed number of values, and Part 2 shows Ekorn's. Iain chose,
in 2026-0057, to have DBIx::Squirrel export it.

## Decisions

- [x] **D1.** Which module exports it, on request?
  DBIx::Squirrel::Tooling, importing it from Ekorn::Pipeline and
  holding it in `:core`, beside `Stop`, `is_stop` and `gather`, as Iain
  proposed on 2026-11-26. It
  reverses Tooling's leaving `is_stage` out as for extending, not
  using, which its POD says and `t/28-tooling.t` checks. Tooling is
  Part 2's (2026-0052's D2), so Part 1 still can't show it: it keeps
  its function with a fixed number of values, which covers the common
  case, and Part 2 imports `is_stage` from DBIx::Squirrel, not from
  Ekorn::Pipeline. The options considered were:
  - DBIx::Squirrel itself: its `import` hands every name to the DBI's,
    for the DBI's constants, so it would need to take `is_stage` out
    first, mixing two jobs in one list;
  - DBIx::Squirrel::Context, beside `iterator`, `result_number` and
    `result_original`: what a stage or a function taking stages asks
    of the run, which `is_stage` isn't quite;
  - a module new to DBIx::Squirrel, which needs Iain's say on its name;
  - DBIx::Squirrel::Stop, beside `is_stop`, which reads oddly for a
    module of that name.
