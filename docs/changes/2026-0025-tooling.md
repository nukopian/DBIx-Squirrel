## Background

What a caller uses to do work with DBIx::Squirrel is made in several
modules: DBIx::Squirrel::Stop, Gather, Context and Stages::Flow,
Batch, Taps and Rows, with sinks, sources and the words from
Ekorn::Pipeline's own modules. The docs' examples import them module
by module, about 30 times in the user guide alone.

Ekorn::Pipeline v0.3.0 has Ekorn::Pipeline::Tooling, which exports
everything a caller uses from one module: nothing by default, by tags
that follow the modules that make the names (`:core`, `:flow`,
`:batch`, `:taps`, `:stages`, `:sources`, `:sinks`, `:words`, `:all`),
leaving out what's for extending the package, such as `is_stage` and
`croakf`, and the operators, a pragma. What its tags hold is public,
so DBIx::Squirrel can build on it.

Of the names DBIx::Squirrel's modules export, checked against Ekorn's
develop at 06e96d5 on 2026-11-13: `Stop`, `gather` and every stage of
Flow, Batch and Taps are Ekorn's own subs, passed on by name;
`pluck`, `as_hash`, `iterator`, `result_number` and `result_original`
are DBIx::Squirrel's alone. No name is exported by both as different
subs.

## Decisions

- [x] **D1.** Does `:stages` include `:rows`? Yes, Iain decided on
  2026-11-13, leaving it to what's logical and sensible: this is for
  convenience, and `pluck` and `as_hash` are the stages a DBIx::Squirrel
  user reaches for first.
- [x] **D2.** `:context` a tag of its own, or part of `:core`? Its own,
  following the module that makes the names, as Ekorn's tags do, and
  in `:all`. Iain decided on 2026-11-13, as for D1.
- [x] **D3.** Do Ekorn's `:sources`, `:sinks` and `:words` come too,
  though a statement is a source of its own? Yes, all three, under
  Ekorn's names: `from_array` and the rest are handy with `pipe`, and
  one module should be enough. Iain decided on 2026-11-13, as for D1.
- [x] **D4.** Is the Sugar left out? Yes, as Ekorn leaves out its
  operators: both are configured on `use`, by a caller who names them.
  So are the operators, `croakf` and the Util functions. Iain decided
  on 2026-11-13: "If that's what Ekorn did, then we do it too."
- [x] **D5.** Do the docs import from it? Yes: the README, the
  reference and the user guide, as Ekorn's do. Iain decided on
  2026-11-13: "Be consistent."
- [x] **D6.** Where DBIx::Squirrel and Ekorn both export a name, whose
  is it? DBIx::Squirrel's, Iain decided on 2026-11-13: "Favour
  exporting the DBIx::Squirrel version of anything Ekorn::Pipeline
  also exports." So each name comes from DBIx::Squirrel's module where
  it has one, and from Ekorn's only where it has none. Today both are
  the same sub; a test checks each name both export is one sub, and
  that both modules' `:all` import into one package without a
  warning, so the two parting is caught. He asked that this be checked
  with care.

## The plan

What: DBIx::Squirrel::Tooling, exporting nothing by default, with the
tags `:core` (`Stop`, `gather`), `:flow`, `:batch`, `:taps`, `:rows`
(`pluck`, `as_hash`), `:context` (`iterator`, `result_number`,
`result_original`), `:stages` (`:flow`, `:batch`, `:taps`, `:rows`),
`:sources`, `:sinks`, `:words` and `:all`; each tag every name its
module exports. The docs' examples import from it.

Why: one module to import from, as Ekorn has, with the same tags, so a
caller moving between the two finds the same words.

Steps:

1. `lib/DBIx/Squirrel/Tooling.pm`, its POD, and
   `t/28-tooling.t`, after Ekorn's `t/23-tooling.t`, adding: each name
   is DBIx::Squirrel's sub where it has one; each name both export is
   one sub; both `:all` in one package, either order, warn of nothing
   and give the same subs; and the stages work on a statement.
2. `Changes`, and the reference's table of modules.
3. The README, the reference and the user guide import from it: the
   guide's set-up and the reference's At a glance import `:all`, each
   has a section on it, and the examples' own imports go; the manuals
   and `README.md` made again.

Done when: the tests pass, coverage keeps its floors, and every
example in the docs runs importing from Tooling.
